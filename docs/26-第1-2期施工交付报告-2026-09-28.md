## 3. 第 2 期：服务端地基

### 3.1 P0（新增，本轮最大发现）：连接池 15 条 + 等连接在事件循环上 🔴

**不是靠读代码发现的，是压测打出来的**（`backend/scripts/loadcheck.py`）。

现象：`sqlalchemy.exc.TimeoutError: QueuePool limit of size 5 overflow 10 reached, connection timed out, timeout 30.00` 抛在 `auth.py:108 get_current_user → db.get(User)`。

根因两层叠加：
1. `db/session.py:29` 的 `create_engine()` **没传连接池参数**，吃 SQLAlchemy 默认 `pool_size=5 + max_overflow=10` = **全站 15 条连接**；每个已鉴权请求光鉴权就占一条。
2. 这些端点是 `async def` 里跑同步 SQLAlchemy → **等连接发生在事件循环线程上**，一卡就是全站卡死（压测里连零 DB 的 `/api/health` 都跟着 20s 超时）。

压测基线（修前，同一台机器）：

| 档位 | A 纯读 P99 · 失败 | A2 写后纯读 P99 · 失败 |
|---|---|---|
| 15×2 | 288ms · 0 | 191ms · 0 |
| 50×2 | 796ms · 0 | **20308ms · 77/100 超时** |
| 50×5 | **20571ms · 169/250 超时** | 20480ms · 54/100 超时 |
| 200×2 | 3665ms · 0 | 5992ms · 2/400 |

`database is locked` 全程 0 —— 但这个「0」**不能当成写侧没问题的证据**：请求先在连接池上死掉了，SQLite 根本没走到报 locked 那一步。

**修法**（`db/session.py`）：显式 `pool_size=20 / max_overflow=40 / pool_timeout=30 / pool_recycle=1800 / pool_pre_ping=True`，四个值均可用环境变量覆盖。容量 15 → 60。

**已验证**：4 档重跑 + 对照实验，50×2 失败 77/400 → **0/400**，50×5 失败 473/850 → **0/850**，`QueuePool TimeoutError` 归零；把池调回 5/10 冻结原样复现。详见 §6。

| ① 只读 P99 不随写事务抖动 | **不通过** | **通过** | **不通过** |
| ② `database is locked = 0` | 通过 | 通过 | 通过 |
| ③ 无孤儿 running | 通过 | 通过 | 通过 |

### 6.4 结论（这才是本轮最值钱的一句）

**是真 P0，而且是雪崩型**——不是变慢，是全站连零 DB 的 `/api/health` 一起 20s 超时。修完的效果分两段：

- **并发 50 以内已健康**（P99 ≤ 1.25s、0 失败）；
- **到 200 并发不再崩但也不快**（P99 约 5s）——瓶颈已经从连接池转移到「单事件循环里跑同步 SQLAlchemy」的串行化。

**所以池调到 60 之后继续调大池子已经没有收益了。** 下一步该动的是 §3.4 那件事（重端点 `async def`→`def` 已经做了 8 个，但 405 个端点里绝大多数还是 `async def` 跑同步 DB）。这也是一条可复算的判断：并发上限已经探到，剩下的不是「池不够大」。

### 6.5 这轮没测出来的

- **生成任务那一档仍未覆盖**（要真 provider key），所以「③ 无孤儿 running」在两轮里都偏弱——孤儿只可能由长任务产生，没跑长任务，「0 个」有一部分是天然为空。
- **200×2 改后反而多了 9 次失败**（连接级 ReadError / RemoteProtocolError，非池超时）。量级比改前的 2 次大但性质完全不同（改前是服务端彻底无响应）；共享机器噪声下不排除偶发成分。
