# jarvis-write 综合评估与方向建议

> 评估日期：2026-09-08 · 代码基线：`main` @ 3d4042a（v0.38.0）
> 评估方法：全仓代码取证 + 真实跑测试 + 竞品实测资料调研（非仅看 README）

---

## 0. 一句话结论

**这是一个工程质量明显高于平均水平、但"宣称的定位"与"实际的投入"严重错配，且核心卖点存在若干"纸面能力"的项目。**

它已经证明了**"能做出复杂系统"**，还没有证明**"写出来的长篇比别人更稳"**。下一阶段的胜负手不是再加功能，而是把已经宣称的三件事——**可控、改得动、不崩**——变成可测量、可对外证明的事实。

## 1. 定位评估：宣称的核心 ≠ 投入的重心

### 1.1 项目对外定位

README 第一行：**"一个可控、改得动、不崩的 AI 长篇小说创作系统"**，价值在于"包在 LLM 外面的控制层"。

> **制片线的 API 代码量是小说核心的 2.1 倍。**

### 1.3 三个刺眼的错配

1. **README 头号杀手锏"大纲级联更新"（自称"同类开源项目里一个都没做"），引擎只有 462 行——比"生日祝福工坊"（855 行）还少 46%。** 一个被称为代差的能力，投入量级排在倒数第四。
2. **8 条产品线**（小说 / 剧本 / 漫剧 / 宣传片 / 情绪短片 / 灵感 / 故事 / 生日祝福）共用一套工作台。生日祝福工坊和"长篇小说一致性引擎"在同一个侧栏里，会稀释专业用户的心智。
3. **"只产提示词、不接生成模型"的制片工坊，本质服务的是短视频创作者，不是长篇小说作者。** 两个用户群、两种付费意愿、两种口碑传播路径。

## 3. 最伤可信度的五处"纸面能力"

这五条的共同模式是：**README/注释承诺了 A，代码实际上做的是 B，而且 B 失败时静默降级，用户无感。**

| # | 宣称 | 实际 | 证据 |
|---|---|---|---|
| 1 | 一致性门禁拦截矛盾章节 | LLM 调用失败 → `return []` → 无 blocker → 章节照常流出 | `consistency/checker.py:197-199` |
| 2 | 章后自动抽取事实写回圣经 | 抽取失败 → `return {}` 静默，圣经不更新但不报错 | `consistency/extractor.py:287-293` |
| 3 | 主审四维评分 | **LLM 自评**（LLM-as-judge），且**默认档位 review 模型 = 生成模型** | `editorial.py:56` + `llm/router.py:78-80` |
| 4 | 动 prompt 前必须跑评测 | 两套 baseline **README 首行即声明"均不作回归基准"**，无 CI 门槛、无判别力验证 | `evals/examples/README.md:3` |
| 5 | SQLite（**可切 Postgres**） | 检索层深度绑定 FTS5 / `json_each` / `MATCH` / `bm25`，PG 无原生等价物 | 迁移 `0008:47-168`、`search.py:118-127` |

> **第 1 条最危险**：项目 slogan 是"不崩"，而一致性门禁恰好在 LLM 出错（超时/429，长篇场景高频）时**静默放行**。这不是 bug，是安全网在最需要它的时候自动撤掉。

**此外还需知道的**：
- **外键约束全程未开启**（`db/session.py:39-45` 缺 `PRAGMA foreign_keys=ON`，`deps.py:50` 注释自证"SQLite 默认不开"，靠手工逐表级联删除）。
- **JSON 解析失败静默返回 `{}`**（`extractor.py:46`），导致四维被 `_clamp_score` 补 0，章节被误判不达标。
- **AI 味指数是确定性算法**（正则 + 统计），**这一项是真的、可信的**——它是目前整个质量体系里唯一可靠的客观指标。

### 4.1 我们真实的差异化（站得住的部分）

1. **时序故事圣经**：`valid_from/valid_until` 区间是真的（`bible.py:106-132` 按区间过滤、支持事实取代），能回答"第 N 章时角色是什么状态"。InkOS 是"真相文件 + SQLite 检索投影"，在"时序查询"这一层我们更深。
2. **大纲级联更新**：`differ.py:170-196` 规则粗筛 + LLM 精判 + `impact.py:22` 下游影响分析（限 30 章）+ 用户勾选后重生成。**从竞争调研看，确实没有同类开源项目做这个。** 但只投入了 462 行，还远没做透。
3. **去 AI 味的量化门禁**：9 类规则是真数据驱动表（`ai_flavor.py:31 _RULES`，权重 0.6~2.0），自愈闭环有多重安全阀（篇幅越界/未降分/统计倒退/过度矫正）。**比 InkOS 的"疲劳词表 + prompt 层介入"更工程化。**
4. **Web 工作台完成度**：正文即界面、diff 逐条验收、双轨对照——InkOS 的 Studio 是后补的，我们的交互深度更好。

### 4.2 我们真实的差距（必须承认）

| 差距 | 严重度 | 说明 |
|---|:---:|---|
| **分发门槛** | 🔴 高 | 人家 `npm i -g @actalk/inkos` 一条命令；我们要 Docker / 桌面安装包 / 源码三选一 |
| **数据校验纪律** | 🔴 高 | InkOS：Zod 强校验，"坏数据直接拒绝，不会滚雪球"。我们：`except: return {}` |
| **审校模型分离** | 🟡 中 | InkOS 明确"写手用 Claude、审计用 GPT-4o"；我们默认 review = quality（同模型自审） |

## 5. 完整问题清单（按优先级）

### P0 — 动摇产品承诺（建议 1~2 周内处理）

1. **一致性门禁静默绕过**（`checker.py:197-199`）：LLM 失败 → 空 issue → 章节流出。
2. **事实抽取 / JSON 解析静默返回空**（`extractor.py:46, 287-293`）。
3. **评测无固化门槛**：`real baseline` 未进 CI，改 prompt 的纪律靠自觉。
4. **主审质量分是 LLM 自评且默认同模型自审**：用户感知的"质量门禁"建立在最不可信的数据上。
5. **文档与实现不符**："可切 Postgres"实为不可切。

### P1 — 架构债（影响长期演进）

6. **外键约束全程关闭** + 手工级联删除（`session.py:39-45`、`deps.py:50`）。
7. **双迁移体系并存**：legacy 43 个 ALTER（失败直接阻断启动）+ Alembic 12 版，无统一版本化。
8. **SQLite 事务纪律靠人工样板**：`db.commit()` 释放读快照的逻辑散落 37 个文件；同步生成路径内部已多次 commit，失败无回滚。
9. **前后端无契约同步**：`api.ts` 93 个手写 interface，后端改字段前端静默失配。
10. **编排上帝类** `pipeline/chapter.py` 788 行、import 30+ 符号。

### P2 — 体验与增长

11. 前端无全局状态，61 个 `useEffect` 拉数无 abort，api 层不支持用户级取消 → 竞态。
12. 超大组件（933 / 779 / 764 行）+ `07-legacy-stages.css` 疑似死样式。
13. 后台 job 是内存态，服务重启即丢；前端要轮询到 30 分钟超时才报错。
14. N+1 查询：`bible.py:75-131` 每实体一次 `find_entity`，单章 10 角色即 10 次查询。
15. 鉴权面：无 refresh / 黑名单（改密不废旧 token）、限流仅覆盖登录注册且 XFF 可伪造。

## 6. 优化与修复建议（按 ROI 排序）

### 6.1 第一优先：把"静默降级"改成"显式降级"（约 2~3 天，收益最大）

**做法**：统一 LLM 调用包装，禁止在关键链路上 `except: return [] / {}`。

- 一致性检查失败 → 必须落一条 `degraded` 标记 + 章首交稿单明示"本章未经一致性校验"，且**状态进 `pending_review` 而非放行**（现在恰恰相反）。
- 事实抽取失败 → 章末标记"本章未抽取事实" + 提供一键补抽。
- JSON 解析失败 → 用已有的 `salvage_json_objects` 抢救（review 链路目前没用它），抢救失败再降级。

**为什么优先**：这一条不改，其余所有"不崩"的宣传都是空中楼阁。改完，slogan 才成立。

### 6.2 第二优先：质量分"脱虚向实"（约 1 周）

- **主轴换成确定性指标**：AI 味指数（已有，可信）、复读率、对白比、篇幅比、事实冲突数（blocker/major，来自检查器）。
- **LLM 判分降级为辅助**：主审四维标注为"AI 参考意见"，且**默认把 review 档指向独立配置的模型**（改 `router.py:78-80` 的默认值，让"自审"变成需要显式选择的选项）。
- **对外口径同步修正**：README 里"主审四维评分"的表述改为"确定性指标 + AI 参考意见"，避免被懂行的用户拆穿。

### 6.3 第三优先：评测立门槛 + 判别力验证（约 3~5 天）

- 把 `baseline-real-po_feng_ji` 立为 CI 硬门槛（跑 mock 版即可，指标不退化）。
- **补一次 mutation test**：故意改坏一个 prompt（比如删掉去AI味反例段），验证指标确实下降。这能直接回答"这套评测到底拦不拦得住"。
- 评测结果落趋势（哪怕是追加一个 CSV），别只落 JSON 文件。

### 6.4 第四优先：降低试用门槛（约 3~5 天，直接换增长）

- **一条命令起服务**：提供 `pipx run jarvis-write` 或 `docker run` 之外的最短路径，README 顶部第一行就是它。
- **用已有的公开分享能力做样例书**（v0.37 刚做的免登录只读链接，正好派上用场）：官网挂 1~2 本**用本系统真写出来的书**，任何人点开就能读。**这比 2000 字功能介绍有说服力。**
- **公开成本数据**：65550 tokens/章、215 秒/章——这是很能打的数字，现在埋在 JSON 里没人知道。

### 6.5 文档诚实化（半天）

- "可切 Postgres" → 要么改成"当前深度绑定 SQLite"，要么真的抽出检索层。
- 建议直接改文案，把省下的精力投到小说核心。

## 7. 后续开发方向

### 核心判断

> **项目现在的瓶颈不是"功能不够"，是"没人相信它写得好"。**
> 已经堆了 8 条产品线，再加功能只会继续稀释。下一阶段要做的不是加法，是**把已宣称的三件事做成可证明的事实**。

### 方向 A（主推）：可信度工程 —— 让"不崩"可测量

1. **长篇压力测试公开化**：用系统真跑一本 50 章以上的书，全程公开：一致性冲突曲线、AI 味指数曲线、每章成本、人工干预次数。**这是唯一能正面回应 InkOS"33 维审计"的方式——用事实而不是形容词。**
2. **样例书官网展示**：复用已有的公开分享能力，官网挂成品书。
3. **"一致性报告"导出**：让用户能导出自己书的健康报告，这是可传播的自证材料。

### 方向 B：把"改得动"做成真代差 —— 从章级级联升级到设定级级联

当前级联是"改一章大纲 → 分析下游 → 勾选重生成"（`cascade/` 仅 462 行）。**下一代的"改得动"应该是**：

> 改一条角色设定 / 一条世界观规则 → 全书扫描受影响章节 → 批量定点修（而不是整章重写）→ 逐条 diff 验收。

这是长篇作者真正的痛点（写到第 80 章发现人设要改），也是**目前没有任何开源项目做到的**。它比"再开一个工坊"值钱得多，而且能复用现有 cascade + consistency + diff 验收的全部基础设施。

### 方向 C：读者视角（InkOS Radar 的启示，可选）

网文作者的真痛点不只是"设定不矛盾"，还有"这章有爽点吗 / 读者会不会弃书"。可以在主审清单里加"读者留存信号"维度（钩子强度、章节结尾悬念、爽点密度）。**注意：这个必须做成确定性+结构化输出，别又变成一个 LLM 自评。**

### 方向 D：制片工坊维持冻结

与 2026-09-05 的既定决策一致：漫剧/宣传片/情绪短片/灵感/故事/生日祝福**只修 bug 不加特性**。理由已在 §1 用数据说明——它们占了 3189 行 API 代码，是小说核心的 2.1 倍，但服务的是另一个用户群。

### 建议的投入配比（下一阶段）

| 方向 | 建议投入 |
|---|:---:|
| P0 修复（静默降级 + 评测门槛 + 质量分脱虚） | **40%** |
| 方向 A 可信度工程（压力测试 + 样例书） | **30%** |
| 方向 B 设定级级联 | **25%** |
| 制片工坊维护 | 5% |

## 8. 一句话给决策

**别再问"还能加什么功能"，改问"怎么让别人相信它已经能写"。**

先把 4 个 P0 修掉（约 2 周），再花 2 周做一次 50 章压力测试并公开结果——这两件事做完，项目的对外可信度会从"README 说自己强"变成"有数据证明自己强"。这比再开两个工坊的价值大得多。
