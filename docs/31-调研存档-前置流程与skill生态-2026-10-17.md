### A.1 AI_NovelGenerator(中文社区最流行的开源桌面版)【中高】

- 仓库(记忆中):github.com/YILING0013/AI_NovelGenerator
- 四步向导:①生成设定(主题/类型/章节数/字数 → 世界观) ②生成目录(全书章节列表,每章标题+一句话粗纲) ③生成草稿(逐章拼入本章大纲+上章结尾+角色状态+情节要点+向量检索历史) ④定稿(扩写润色 + 自动回写角色状态与情节要点)。
- 中间产物:自由文本/轻结构化 txt + JSON(Novel_setting.txt / Novel_directory.txt / character_state.txt / plot_arcs.txt)+ embedding 向量库 + config.json。
- 交互:向导式 + 逐步确认,每步可手改再进下一步;**无多候选比选**(不满意只能重跑)。
- 独特机制:①逐章回写的状态账本(最早的「幂等设定回写」朴素实践);②向量检索历史召回;③「草稿→定稿」两遍生成。
- 社区批评:粗纲只有一句话导致章节易跑偏;长书后期角色状态文件膨胀后注入质量下降。

### A.2 SillyTavern World Info / 角色卡体系【高】

- github.com/SillyTavern/SillyTavern;卡规范 Character Card V2/V3。
- 几乎没有「前置环节」:「设定即注入」。角色卡结构化 JSON;World Info 词条带 keys/secondary_keys、选择性逻辑、插入位置与深度、概率触发、sticky/cooldown、token 预算、递归扫描。
- 独特机制:**mention-triggered 注入**(建库+按提及检索注入,天然抗上下文膨胀);条目级插入位置控制;卡是可分发、可版本化的结构化资产。
- 批评:为角色扮演而非长篇小说设计;关键词不命中时设定被「埋掉」。

### A.3 Novelcrafter Codex(商业,理念参考)【中】

- novelcrafter.com;Codex = wiki 式实体库(角色/地点/物品/传说,可嵌套、自定义字段);Outline 板排场景;场景卡写 beats;**被场景提及的 Codex 条目自动注入 prompt**(可手动 pin,实时显示 token 数);Matrix 网格(场景×条目)一眼看到谁在哪章出场。
- 独特机制:mention→自动注入→实时 token 计量闭环;Matrix 出场规划;场景卡作为大纲与正文之间的中间粒度。

### A.4 Sudowrite Story Bible(商业,前置流程最重的一家)【中高】

- Braindump(倒点子)→ Story Bible 自动填充 → 大纲 → 逐章 Beats → 逐 beat 生成正文。
- 独特机制:Braindump→Bible 的「一键从点子长出设定集」;beat 作为生成单元(比一句话粗纲细、比逐句细纲灵活的甜点粒度)。
- 批评:贵;文风被诟病 AI 味;Story Bible 填太满会锁死后续发挥。

- Blinkdl/AI-Writer【中】:前置≈一个输入框,参考价值低。墨狐AI【低】:未查到开源仓库。
- NovelAI Lorebook / KoboldAI World Info【中】:与 SillyTavern 同范式。

### A.6 论文/框架类

- **STORM**(斯坦福,NAACL 2024)【高】:先调研后大纲;多视角提问→带检索的写手×专家对话收集素材→知识整理裁剪→**从素材笔记归纳大纲**;Co-STORM 支持人类插话。启发:大纲由素材反推;多视角提问对抗单一视角跑偏。
- **Re3**(EMNLP 2022)【高】:Plan→Draft→Rewrite→Edit;**计划是活状态**(边写边更新);矛盾/重复检测后定向重写;生成多候选按相似度重排选优。
- **DOC**(ACL 2023)【中高】:**先草稿后大纲**(让模型先写草稿再从草稿抽两级细纲,质量高于凭空写大纲);生成时按块以细纲为条件 + **recalibration**(按已生成内容实时校准后续细纲)。
- **Agents' Room**(DeepMind,ICLR 2025)【中】:规划团队(角色/设定/情节 agent 分工再合并)+ 写作团队(写手+critic 审稿打回)。
- **LongWriter/AgentWrite**(THUDM,2024)【高】:长文分解成带「目标字数+内容要点」的子任务再顺序写。
- **Dramatron**(DeepMind,2022)【高】:log line→标题/角色→分幕 beats→对白,**每步用户可编辑后才进下一步**(最早的「交稿单」形态)。
- WebNovelBench【低】:简介→全文生成任务 + 多维叙事质量评测,维度可反用作自检清单,细节未核实。

### A.7 横向对比(该报告自己的总结)

共同模式:①管线同构(设定集→大纲→场景/beat 细纲→逐单元生成;「一步从点子到正文」的长篇工具无一成功);②中间产物走向结构化(为了按需注入与一致性校验);③设定是活的(初始最小+随写生长+写后回写);④注入按相关性而非全量;⑤交互上没有纯自动(纯一次性生成只存在于短篇)。

分歧点:①大纲该多细(较优解是「场景/beat 粒度 + 校准回路」);②设定写前锁死 vs 边写边长(**回写机制质量差异巨大;「回写先入待确认队列、用户拍板后才入库」在开源项目里几乎没有,是明确空白位**);③候选比选与打回(论文已证、工具未做的最大缺口)。

对长篇平台最可迁移的 5 条:①前置产物全部结构化可注入可版本化;②大纲「场景/beat 级+两级粒度+校准回路」;③设定走「建库+相关性注入+token 预算」+ 逐章回写账本;④回写走待确认队列(差异化点);⑤关键前置节点多候选+比选+定向打回。

### B.4 该报告的总结:共同设计模式(9 条)

1. 先问后写,且提问分级(必答核心层→可跳过定制层→自由描述兜底)。
2. 选项式提问 + 偏好排序(历史偏好排前+⭐标记;静默写入偏好文件)。
3. 分步确认 + 阶段门禁 + 显式「禁止确认区」。
4. 每步产出可验收的中间物并落盘(文件系统当记忆;status 文件是唯一真相源)。
5. 强制验证与硬阻断(验证脚本 + checkbox 清单 + 状态锁)。
6. 质量门禁与周期性审查(双审查;每 2 章 5 专职审查;确定性检测器作唯一评分源)。
7. 一致性工程(事实锁+哈希锚点;分层上下文组装;伏笔=待偿债务;状态卡固定栏位+硬上限;死后出场检测)。
8. 多候选生成让用户选(5 个钩子变体;8-12 个 what-if;3-5 个书名)。
9. 验收式反馈(每个测试报 pass/weak/fail + 原因 + 修订;校准段落第 1 章回填;lessons_learned)。

### B.5 最适合移植进 jarvis-write 的机制(按优先级,该报告原序)

1. what-if→logline→stress test 的「验收式提问」(story-skills)。
2. 文风基准文件 + 第 1 章后自动回填校准段落(chinese-novelist)。
3. 事实锁 + 哈希锚点 + 改稿后旧审查失效(MyNovel)。
4. 规划窗口防抢跑(MyNovel 每 50 章)。
5. 伏笔回收时回读埋设原章 + 超期/变义/缺因果桥审查。
6. 状态卡固定栏位 + 硬上限 + 本章技法至多读一份(oh-story)。
7. 每步验证脚本 + checkbox 清单 + 状态锁(novel-writer)。
8. 母子 skill 编排 + 阶段门禁(save-the-cat)。
9. Reader Testing(doc-coauthoring)。
10. 去 AI 味:确定性检测引擎作唯一评分源 + 模式分级 + CI(avoid-ai-writing)。
11. 每章主功能→技法文档路由 + 周期审查 agent 分工(Crucible)。
12. 故事概念结构化:premise/counter-premise + 三层赌注 + 按活动部件数选形式(story-skills)。

一句话结论:这个生态里最「厉害」的写作 skill 都不是提示词写得花,而是**把写作过程工程化**——先问后写、每步落盘、脚本验证、硬门禁、哈希锚点、伏笔当债务管。中文网文 skill 在「长篇一致性工程」上走得最远,英文生态在「前置提问法与读者测试」上更精细。
