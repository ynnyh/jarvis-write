# 风格包 Skill 化：把「去 AI 味」的治疗权交给用户？

> 评估日期：2026-09-10 · 代码基线：`main` @ 95afc8b
> 评估方法：全仓代码取证（去味链路 · 样式装配 · 评测底座）+ WorkBuddy Skill 协议格式审查
> 结论性质：**支持这个方向，但「咱们只需要做好门禁」这句需要修正三处**

---

## 0. 一句话结论

**方向成立，改造成本比想象低得多（最小 5 处改动），但「交出治疗权、只留门禁」这个分工不成立——因为当前门禁是一套写死的审美标准，它拦不住自定义风格，只会误杀它。**

真正该做的不是「退到一旁」，而是**把门禁从一道升级成三道**：负向门禁（不许喊通用 AI 腔）、正向门禁（写得像不像你的范文）、回归门禁（换包前后故事不许劣化）。

还有一个产品层面的关键判断：**不要让用户手写 skill 文本**。绝大多数网文作者写不出 prompt，但都拿得出自己最满意的三段字。**从范文反推**才是这条路的杀手锏。

---

## 1. 你的直觉对在哪

### 1.1 「去 AI 味」和「有风格」是同一枚硬币的两面

AI 味的本质是**统计平均的中文书面语**——大模型输出的是训练集里最常见的表达。所谓「风格」，就是**系统性地偏离这个平均**。所以：

> 不可能在「去除通用腔」之外单独实现「写出个人风格」。去除的平均部分越多，就越需要一个正向锚去填充它是什么。

现在的系统只做了前半件事：

| 环节 | 实现 | 性质 |
|---|---|---|
| **判定**（AI 味评分） | `ai_flavor.py` L31-125 共 8 类正则 + 4 个统计指标 | 纯规则，零 LLM，天然就是门禁 |
| **治疗**（定点改写） | `prompts/polish.py` L14-27 `_DEAI_RULES` → `DEAI_REWRITE_PROMPT` | **prompt 文本硬编码在代码里** |
| **第二条治疗** | `pipeline/chapter.py` L191-223 `_PROSE_REWRITE_DIRECTIVE` | 主审 prose 维度触发，同样硬编码 |
| **正向锚** | `voice_key` 胶囊 + `voice_sample` 范文 | **可插拔，但很弱** |

也就是说：治疗的方向、口径、禁则，全部由我们团队在代码里定义，用户改不了一个字。

### 1.2 系统其实早就承认「要像某个人」，但机制很弱

现有三处可配置项拼出了这个诉求的雏形：

- `voice_key`（`Prompts/style_capsules.py` L40-153）：**只有 8 个内置作家胶囊**（鲁迅、余华…），加一个要改代码。
- `voice_sample`：作者自备范文，但 `render_voice_block` 硬截断到 **1200 字符**。
- `project.style_memo`：随书累积的文风备忘，每章增量更新。

**这三样加起来，承载不了一位作者的真实文风。** 用户想要更多，是完全正常的诉求。

### 1.3 而且用户已经在用手写的方式绕过我们了

`WritingCard`（`db/models/writing_card.py`）——「写作手法卡」，用户自己写文本规则、勾选启用、注入正文生成与去味。这就是**民间版的用户 skill**，而且已经在被使用。

> 用户没有等你开口，就已经自己在攒规则包了。这是最真实的需求信号。

## 2. 但「只做好门禁」不成立：三个漏洞

### 2.1 漏洞一：现门禁会**误杀**自定义风格（最严重）

`ai_flavor.py` 的规则库表面查的是「AI 腔」，实质隐含了一套**「我们认为的好中文小说」**的审美标准。一旦允许用户追求任意风格，它就从裁判变成了暴政。

举四个真实的误判（`ai_flavor.py` 逐条对照）：

| 规则（位置/罚分） | 正则判定 | 被误杀的风格 |
|---|---|---|
| 欧化中文 L~135（1.2） | `对于X而言`、`扮演着…角色`、`随着X的发展` | **民国/留学题材**的译制腔正是角色设定本身 |
| 比喻连接词癖（0.6） | `仿佛`/`宛如`/`好似` 出现即罚 | **抒情、古风、散文向**写得越多罚越重 |
| 情绪标签直喊（1.0） | `感到/心中 + 绝望/愤怒/复杂` | **第一人称心理流**、意识流必踩 |
| burstiness `_BURSTINESS_RED=0.4` | 句长标准差/均值低于 0.4 判 AI | 追求**汪曾祺式平匀**的作者反被判 AI |

注意最后一条尤其讽刺：这条规则的注释写着「人类参考 0.6-1.2」，可人类写作风格的范围远不止这半段。

**推论：** 交出去治疗权之后如果不改门禁，用户会看到「我按自己的风格写 → AI 味分数暴涨 → 系统判定我写得像机器人」。这是必然而非或然。

### 2.2 漏洞二：门禁管的是「不像 AI」，管不了「像不像你」

AI 味评分（`ai_flavor_report`）的输出是一个「错误计数」——它只能告诉你**哪里不对**，永远无法告诉你**对不对**。

现在的用途也很克制：只作自愈门槛 `DEAI_GATE_SCORE = 6.0`（`polisher.py` L59），**不进一致性门禁、不导致隔离**，只在概览页展示一个徽章。

一旦交给用户 skill，缺的就是这道正向判定：

> 缺失的这道门回答的是另一个问题：**「这段文字，跟作者自己认可的范本，是一个人的手笔吗？」**

正向判定天然是模糊的——同一位作者不同时期的笔触也会有差异，所以它注定会错。但没有它，系统就失去了对「风格」这件事的全部话语权——而这恰恰是我们想保留的价值。

### 2.3 漏洞三：门禁挡不住「写着写着崩了」

现在的去味是在**正文已过门禁之后**执行的最后一刀（`chapter.py` L695-704），且它是安全收敛的：任何一轮失败都**丢弃本轮、保留当前最好版本**（`polisher.py` L240-264）。

用户自带包之后，风险维度变了：

- 篇幅与节奏：去味在字数守卫之后执行（`chapter.py` L695-704），风格激进的包若引入大量扩写/压缩，**没有任何后续环节会再校一次字数**
- 情节一致性**不会**被现有门禁挡住——因为去味跑在门禁之后，之后只剩 `dedup_paragraphs`（只删重复段）
- 也就是说：**一个风格激进的包可以把书写崩，而现有门禁全程绿灯**

### 2.4 还有一层：反馈太晚，试错代价太高

现在的顺序是「写完才知道」。作者换了一个包，要**整章跑完整条流水线**（草稿→定稿→门禁→审定→去味）才能看到效果，中间任何一环出错都是整章重来。

用户探索自己风格的过程需要**低成本试错**——几百字的片段预览，而不是跑完整章才看到结果。现状恰恰相反：**只有把盲盒从头到尾写完，才知道这个包对不对。**

## 3. 真正的产品答案：让用户给范文，而不是写 skill

这是我认为最重要的一条建议。

### 3.1 为什么不是「手写 prompt」

先看清现实：我们的用户是**网文作者**，不是 prompt 工程师。

| 用户能提供的 | 可用性 |
|---|---|
| 写出结构良好的 LLM 指令 | **极少数** |
| 说出「我要冷峻、短句、不煽情」 | 多数可以 |
| 拿出「我最满意的三段字」 | **几乎 100%** |

逼用户写 prompt，等于把最高频的需求门槛抬到最高。

### 3.2 杀手锏：从范文反推规则包

系统已经有 `extractor`（事实抽取）这类「读文本→出结构化规则」的 LLM 能力。**同样的能力用来提炼风格**，产品形态就变了：

```
用户贴 3-5 段自己满意的字（2000-5000 字）
        ↓  提炼（一次性，可缓存）
   风格卡：句长节律 / 用词偏好 / 修辞倾向 / 禁用表达 / 视角与距离
        ↓  用户勾选微调（可读、可改、可删）
   生效：草稿 + 定稿 + 去味 三处同时注入
```

这才是别人做不了、而我们可以做的事：**他们让用户写 prompt，我们让用户贴范文。**

### 3.3 但手写通道要保留

高级用户需要精确控制。所以是**双向**：

- **默认路径**：贴范文 → 反推 → 微调（面向大多数人）
- **高级路径**：直接写规则文本 / 导入 SKILL.md（面向少数人）

## 4. 架构建议：三层包 + 三道门禁

```
                 ┌──────────────────────────────────────┐
   用户侧         │  L2  兼容 SKILL.md（生态互操作，可选）  │
   可插拔部分      │  L1  风格包 Style Pack（导入/导出/分享）│
                 └──────────────┬───────────────────────┘
                                │ 叠加（不可覆盖）
                 ┌──────────────▼───────────────────────┐
   系统保底       │  L0  内置基线（现有 ai_flavor 正则       │
                 │      + _DEAI_RULES，永远生效）          │
                 └──────────────────────────────────────┘

   验收侧（这才是我们的核心价值）
   ┌─────────────┬─────────────────┬────────────────────┐
   │ ① 负向门禁   │ ② 正向门禁（新增） │ ③ 回归门禁（新增）   │
   │ 现有正则     │ 风格指纹/稳定度   │ evals 的 gate       │
   │ 不许喊通用腔 │ 像不像你的范文    │ 换包前后不许劣化      │
   │ → 需支持     │ → 这是真正的      │ → 复用现有评测底座    │
   │   按包豁免   │   新增价值        │                    │
   └─────────────┴─────────────────┴────────────────────┘
```

**关键设计约束：L1/L2 只能叠加在 L0 之上，不能替换 L0。**

理由：`_DEAI_RULES` 不是凭空写的，它是 50 章压测校出来的（官方渠道 37 章 AI 味均值 2.51，跑通的章节可达 1.0）。这是我们迄今最有价值的隐性资产，不能被用户的糟糕包一键抹掉。

### 三道门禁具体长什么样

**① 负向门禁（改造，非重建）**

把现有 8 类规则从「一律生效」改为「可按包豁免」。风格包里声明一条 `exemptions: [欧化中文]`，则该规则的罚分在此书下调或关闭。

> 改造点只有一处：`ai_flavor_report` 接受一个 weight override 参数。`ai_flavor_config` 已有热配机制（`admin.py` L329-435），照抄其形态即可，但需按书存储而非全局。

**② 正向门禁（新增，核心新增价值）**

三类可计算信号，注意**不要只用 LLM 判定**：

| 信号 | 计算方式 | 判什么 |
|---|---|---|
| 句长节律距离 | 本章 vs 范文的句长分布（μ、σ、分位数） | 节奏像不像 |
| 用词偏离度 | 本章词频分布 vs 范文，取 KL 或余弦 | 用词像不像 |
| 风格 LLM 判定 | 匿名双盲：两章混排，问「是否同一作者」 | 综合观感 |

前两条是**免费的、确定性的、可回归的**；第三条做补充。这个顺序很重要——如果只有 LLM 判定，我们就回到了「凭感觉」，无法做 CI 门禁。

**③ 回归门禁（新增，但主要复用）**

`evals/runner.py` 的 `run_fixture` 已经是全链路真跑，并记录 `flavor`（L209）与 blocker 通过率（L249）。加一个「挂载包」参数后，同一夹具可以跑：**baseline vs 启用包**，看三件事：

- AI 味分数是否改善
- **其他维度（连贯/情节/人物）不许劣化**
- 门禁 blocker 数不许上升

这就把一个包好不好，**从嘴上说说变成可以出具报告**。

## 5. 会不会把自己的核心价值掏空？

你可能会担心：风格都让用户提供了，我们还有什么？

我的判断是**不会，反而升级。** 类比 CI/CD：

> CI/CD 不关心你写什么代码，它保证「可构建、可测试、可发布、出错能回滚」。它的价值随着被管生态的复杂度增长而增长，从不因为「代码不是它写的」而贬值。

jarvis-write 的定位（README 第一行）是**「可控、改得动、不崩」**。当风格这件事被下放给用户，我们的角色就从「写得好的那个人」变成「保证写一百万字不崩的那套控制层」——**这跟既定定位完全吻合，而且更难被替代。**

真正会掏空自己的做法是反过来的：继续在 `_DEAI_RULES` 里堆砌我们对「好文风」的想象。那是永远打不赢的仗——每个作者心里都有一个「好」。

## 6. 风险清单与对策

| # | 风险 | 严重度 | 对策 |
|---|---|---|---|
| 1 | **Prompt injection**：用户包里夹带「忽略以上指令」 | 高 | 净化层 + 结构隔离——用户文本只作为**素材**（被引用的描述），不作为**指令**执行。与系统指令分层，不可跨越 |
| 2 | 现门禁误杀自定义风格 | 高 | 负向门禁支持按包豁免（见 §4 ①） |
| 3 | 激进包把书写崩 | 高 | 回归门禁 + 章快照可回滚（现状已有去味失败保底，需扩展到整链路） |
| 4 | 包质量无监管，用户踩雷甩锅我们 | 中 | **包质检标签**：上架/启用前跑一次 evals，出具「AI 味 -X%、连贯 ±Y、blocker ±Z」报告 |
| 5 | 生态碎片化，无人分享无人维护 | 中 | 包可导入/导出/分享；我们也维护官方精品包作为样板 |
| 6 | 迭代知识流失（压测校准的规则被绕过） | 中 | L0 不可覆盖，只能叠加（§4 设计约束） |

**第 1 条要单独强调**：它不是「自定义格式就能躲开」的——只要把用户自由文本拼进 prompt，风险就存在。所以它不是「要不要做 skill」的决策变量，而是**做任何形式的用户自定义都必须付的固定成本**。

## 7. 可行性：接缝已经存在，成本很低

调研确认的三条可用接缝：

| 接缝 | 位置 | 覆盖 |
|---|---|---|
| **voice 注入缝**（最优） | `assembler.py` L136-152 `voice_block_of` → `render_voice_block` | 草稿/定稿（`chapter.py` L308-311）+ 去味（`polisher.py` L408），**天然覆盖三处** |
| **写作手法卡** | `tendency/cards.py` L40 `render_cards_block` | 已是「用户写规则→注入」的完整闭环，但**未覆盖规划阶段** |
| **自定义插入** | `assembler.py` L99-103 `_custom` | 用户额外要求原样注入 |

**成本估算（已逐处数过）：**

- **方案 A｜独立「风格包」字段**：后端 3 处（`style_profile.py` 字段与读写、`voice_block_of` 读新 key、`render_voice_block` 渲染）+ 前端 2 处（`api.ts` 类型、`ArchPanel.tsx` UI）+ 评测挂载 1 处 ≈ **5-6 处小改动**
- **方案 B｜复用写作卡试水**：后端 **0 改动**，仅 `CardsPanel.tsx` 加「标为风格包/导入」≈ **1-2 处**

> 注：`assemble_tendency` 的插入位点有约 12 处，但**不必动它们**——走 voice 缝即可。若希望风格包同时影响大纲/建筑/灵感阶段，才需要追加。

评测侧：`evals` 的 `compare`/`gate`（`__main__.py` L224/L237）可直接复用，需给夹具加「挂载包」参数（约 1 处）。

## 8. 落地路径：三阶段

### 阶段 1｜把治疗权先开一个口子（约 5 处改动）

新增「去味规则」可编辑字段，替换/扩展 `_DEAI_RULES` 的注入。保留 L0 兜底。

> 建议**先走方案 B**（复用 WritingCard，1-2 处）做一周灰度，确认用户真的会往里写东西再做 A。**代码成本极低的时候，最大的风险是做多了。**

### 阶段 2｜风格包 + 正向门禁（真正的护城河）

- 风格包：可导入导出，**从范文反推**生成，支持一书一包与多包切换
- 正向门禁：句长节律距离 + 用词偏离度 + 盲评 LLM
- 回归门禁：evals 挂载 + 出具包质检报告
- 片段预览：换包后先用几百字试写，不必跑完整章

### 阶段 3｜兼容 SKILL.md + 分享生态

**关于要不要原生兼容 SKILL.md 格式**，调研结论鲜明：

> **兼容，但只消费其语义子集。**

理由：SKILL.md 是「YAML frontmatter + Markdown body」的纯文本约定，不绑定任何 Agent 运行时，解析成本近乎零（环境缺 `pyyaml`，需装；frontmatter 用正则切 `---` 即可，约 30 行）。兼容意味着能吃 WorkBuddy/Claude 生态的现成资产，用户不用学新格式。

但必须裁剪：我们**只读 `name`/`description`/body 里与文风相关的段落**，忽略 `allowed-tools`/`scripts/`（绝不执行 skill 里的脚本），并强制过净化层。（补充事实：SKILL.md 规范本身对 `scripts/` **无沙箱、无签名约束**，这也正是我们不能执行它们的理由。）

## 9. 怎么验证：先花小钱买个确定性

按项目纪律（动 prompt 前必须跑评测），建议先做一次**低成本先验**，而不是直接开做：

```
同一黄金夹具（po_feng_ji）× 3 个候选包
  ① 基线（现有 L0）
  ② 抒情古风向（预期会暴露「比喻连接词癖」误杀）
  ③ 硬汉短句向（预期验证 burstiness 能否受益）

看三件事：mean_flavor 的变化方向、pass_rate/blockers 是否劣化、
          「② 被误杀」这个预判成不成立
```

**这一步的意义**：如果 ② 真的被正则误杀，那么「门禁必须升级」就从我的推断变成实测事实，方向的优先级也随之确定。

> ⚠️ 这一轮要真跑模型。按事前约定：官方 key 需错峰（北京 12:00-14:00 或 18:00 后），3 轮 × 10 章量级约 **¥3-5**。是否开跑需你点头，我不擅自发起。
