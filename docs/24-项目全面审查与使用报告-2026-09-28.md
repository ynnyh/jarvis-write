## 1. 总评

**这是一个"工程纪律远高于产品成熟度"的项目。** 架构门禁、测试密度、静默降级的显式化、单测 60% 的比例——这些在开源同赛道里排第一梯队，本次没有发现"能跑但会静默出错"的系统性问题（16 号文档点名的四类静默降级全部已修）。

但它有**两个被规模掩盖的结构性问题**，17 天里没人碰过：

1. **性能与安全的假设仍是"单机单人"**。405 个 `async def` 端点里跑同步 SQLAlchemy、长任务跨 LLM 调用持有写事务、`jobs` 表把整章正文塞进 JSON、**默认管理员口令 + 限流键可由请求头伪造**——这四条在 5 个用户下无感，在 50 个并发生成时会直接变成"全站卡顿 / database is locked / 被接管"。
2. **产品"皮"落后于"骨"**。开书向导 6 屏 12 次拍板、成本在生成前不可见、唯一的说明书指向 2026-08 已退役的顶栏、漫剧步骤 6 项却写"五步"、一段 `docs/22` 内部注释漏进了用户界面。

**以及一条没人提的最大机会**：`docs/14` 判定的头号差距"无检索层"至今零进展（全仓 `embedding|vector|cosine` 命中 0），而"生成薄"那一半已经靠场次制补上大半。**质量天花板的钥匙现在只剩检索这一把。**

## 4. P0 —— 会真出事的（本轮新发现，旧文档无）

### P0-1 默认管理员口令 + 限流键可伪造 = 完整接管链 🔴
- `app/config.py:92` `admin_password: str = "admin12345"`；`app/migrate.py:552-567` 首次启动自动建号、**只 warning 不拒绝启动**。
- `app/main.py:118-132` 启动自检**只**校验 `jwt_secret`，**不查** `admin_password` / `invite_code`。
- `app/ratelimit.py:45-49` `client_ip()` 取 `x-forwarded-for` **第一段**——完全由客户端控制；规则只有 login / register 两条（`:33-36`）。
- `tests/test_ratelimit.py:41-47` 把"换 XFF 即换桶"**当成期望行为编码**——这个攻击面从未被审视。
- `app/api/admin.py:140-158` 管理员可 `reset-password` 任意用户 → 拿到 admin 即逐个接管。

**改造**：
1. `main.py:_assert_secure_config()` 增加：`app_env != "dev"` 且 `admin_password == 默认值` → 拒绝启动（与 jwt_secret 同一模式）。
2. `ratelimit.py:client_ip()` 默认只用 `request.client.host`；新增 `settings.trust_proxy_headers: bool = False`，为真时读 XFF 且**取最右一跳**。
3. login 追加 per-username 计数桶，与 IP 桶双限。
4. `tests/test_ratelimit.py` 补 `test_xff_cannot_rotate_bucket`。

### P0-2 `async def` 端点里跑同步 DB —— 事件循环是全局单点 🔴
405 个路由**无一例外**都是 `async def` + 同步 `Session`。FastAPI 只把**同步**端点丢进 threadpool，`async def` 的函数体在事件循环上跑：
- `api/admin.py:88-93`（`db.query().group_by().all()`）
- `api/consistency.py:369/422`（拉 200 章大纲 + 圣经进内存）
- `api/misc.py:284/298/395/411/438`（epub/docx/zip 导出，纯 CPU+IO）
- `api/project_io.py:76-110`（整包 JSON 导入）

**后果**：一次 200ms 的查询会让 SSE 心跳（`live.py:36` `_POLL_S=0.12`）、`/api/jobs` 轮询、**其他用户的所有请求**一起卡 200ms。50 并发下是"全站卡顿"而不是"某请求慢"。

**改造（零风险、当天可做）**：把上面这 8~10 个最重的端点签名从 `async def` 改成 `def`，FastAPI 自动走 threadpool，**零行为变化**。再加一条门禁：新端点不得在 `async def` 里直接 `db.query/execute/get`。

### P0-3 长事务跨 LLM 调用 —— `database is locked` 的残余根因 🔴
`api/chapters/_job.py:45-55`：`SessionLocal()` → `session.get(Project, ...)`（**已开读事务**）→ `await generate_chapter(...)`（内部几十次 `await adapter.ask()`，单章数十分钟）→ 才 `commit()`。

WAL 仍单写者，且**读事务升级写事务时若期间有别的连接提交，SQLite 直接返回 `SQLITE_BUSY_SNAPSHOT`（不可重试）**——这正是 `busy_timeout=30000` 救不了的那类。`AGENTS.md` 写的"worker 里自己开 SessionLocal，别跨 LLM 调用持有 session"这条纪律，**在主链路上并没有被遵守**。

**改造**：① 把 `generate_chapter` 的读依赖改成"短事务里取快照后 `session.close()`"，生成过程零持有；② 下线 `api/chapters/generation.py:64-94` 的同步 `/generate`（无去重、持长事务，纯负债，前端已走 async 版）；③ 加"两个并发 job 各自 commit 不报错"的回归测试。

### P0-4 上传无体积上限 → OOM 🟠
`api/project_io.py:91-96` `await file.read()` **零上限校验**（同文件 import-book 在 `:128` 有 120MB 上限）；`main.py` 没挂任何 `Content-Length` 中间件；`engines/project_io.py:135` 对导入 JSON 的每张表**无行数上限**。

**改造**：`UploadFile.read(MAX+1)` 判长 + 统一 `Content-Length > 128MB → 413` 中间件 + 每表 2 万行护栏。

### P0-5 最贵的一次调用不记账 💰
`llm/base.py:836-852` 的 `_record_usage` 在 `except EmptyContentError` **之后**、只在拿到 `resp` 时调用。而"推理模型思考吃满预算"这条路径（`base.py:747-754`）恰恰是**最贵**的一次（16k~32k token），连试三轮**全部不记账**；`with_retries`（`base.py:320-350`）的中间重试消耗同样漏记；`:785-786` 还把写库失败 `except: pass` 吞了。

**后果**：`/api/usage` 与 `admin.py:503 quality_overview` 的截断率判断都建立在残缺数据上。**这是"用户自带 key"模式——账不准就等于没法计费、没法判断渠道健康度。**

**改造**：记账下沉到每次 attempt 内部；写库失败改 `logger.warning(exc_info=True)`；补"空正文重试 N 次 → usage 行数 == N"的测试。

### 6.3 门禁该补的判据（防复发，不加豁免）
1. **禁内部注释外泄**：用户可见 JSX 文本里出现 `docs/\d+` 或 `TODO/FIXME/XXX` 即失败（挡住 ① 的复发）。
2. **禁裸 Markdown 记号**：字符串字面量里出现 `**` 且该串会进 JSX 文本 → 失败（挡住 ②）。
3. **禁过期 UI 术语**：维护一份"已退役组件词表"（`顶栏`、`workbench`、`.topbar`），源码中出现即失败——**这一条能同时挡住 ③ 的复发和旧外壳复活**。
4. **步骤编号自洽**：`StepBar` 的 `steps.length` 必须等于同屏文案里的最大序号（挡住 ④）。

## 8. 战略层（这一节没人写过）

**8.1 护城河在哪。** 不是"AI 写小说"（这个赛道 8 个项目都在做），而是三样：
① **时序故事圣经**——能回答"第 N 章时这个角色是什么状态"，同赛道没有第二家做区间事实；
② **级联**——改章纲/改设定 → 下游影响分析 → 勾选重生成，目前开源一个都没有；
③ **去 AI 味的工程闭环**——量化指标 + 定向重写 + 复测 + 没改好自动回退，比 InkOS 的"词表 + prompt 介入"深一层。
这三条都写在 `docs/14`，经过 17 天仍然成立。**但它们没有一条变成对外可见的事实。**

**8.2 最大的一块钱没花。** `docs/14` 判定"无检索层"是当前质量天花板的第一杀手，17 天零进展。同赛道里 novel-creator-skill 把答案写在脸上：**写前只读 4 个文件，RAG 只回 Top-K**。而我们草稿一次注入 31 个上下文块（`prompts/chapter.py`）。**这不是要不要上向量库的问题，是"把全量灌改成按需取"的问题**——SQLite FTS5 + 结构化过滤（本章出场人物 / 场景地点 / 伏笔状态）就能拿回 80% 的收益，零新依赖，2 周可上线，且 A/B 评测底座（`evals/`）现成。

**8.3 分发是最便宜的护城河，也是最没做的。** 对标：一条命令 / 一个安装包 / 三条命令。现状：四种入口、无 demo 书、`DEMO.url` 未配。**挂一本真写出来的书（用现成的免登录分享链接），比再写 2000 字功能介绍有用一百倍。**

**8.4 一个可能被忽略的商业杠杆。** Sodarie Novel 允许用户"直接调用本机已登录的 Claude Code / Codex CLI，用订阅额度写，不另花 API Key 的钱"。我们要求用户自备 key —— 这是**公网试用转付费的最大摩擦点**。至少可以把"中转站/代理"做成开箱即用的预置配置（我们已有 `provider_configs` 多配置体系，成本很低）。

**8.5 取舍提醒。** 五条出片线（drama / promo / clips / birthday / anime）在 17 天里新增了场次制、爽点地图、剪映导出三条能力。**但 `docs/14` 指出的"漫剧线质量关卡最空"至今没补**——它代码量最大（3,982 行）、离钱最近，却是唯一没有格式门禁/版本回退/一致性校验/审校回炉的线。**要么补齐它，要么明说只做深小说线。** 两头都想要的结果就是现在这样：每条线都有"最全的节点"，没有一条"跑得顺"。
