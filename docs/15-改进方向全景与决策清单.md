# jarvis-write 改进方向全景（不加兼容约束版）

> 撰写日期：2026-09-10 · 前提：**激进重构现有代码库 · 质量优先（成本可翻倍）· 三条线一起设计**
> 性质：**待你抉择的方案清单**，不是已定稿的执行计划。每条给出「现状 → 问题 → 推荐方案 → 备选 → 代价 → 待决问题」。
> 配套：`docs/14-全面调研与综合评价-2026-09-10.md`（诊断依据）；本文件是它的「怎么改」续篇。

## 0. 总纲：一句话架构判断

**现在的系统是「一个厚校验层包着一个薄生成层」。要做的不是给薄的那层打补丁，而是把它换成正确的形态：**

```
现状                                    目标
─────────────────────────────           ─────────────────────────────
31 个上下文块 ──全量灌──▶ 1 次草稿       事实层 ──按需检索──▶ 场景编排 ──逐场景──▶ 写作
                                        （谁的、哪一条、         （这一场要         （只带这
                                          什么时候的）            什么效果）        一场的事）

1 次定稿 ──▶ 9 次校验/修补/记账          场景级验收 ──▶ 全书级验收 ──▶ 只重来坏的那一场
```

**核心命题：把「章」从「生成单元」降级为「容器」，把「场景」升格为真正的生成单元。**

理由（三条互相咬合）：
1. **注意力预算**：一次性给模型 31 个约束 + 3000 字任务，它必然走"平均用力"的安全策略 → 白水。**一次只给一个场景的任务和该场景相关的约束，它才有力气"放开写"。**
2. **验收粒度**：现在主审发现"第 2 段垮了"只能整章重写（重新抽签，且丢掉写得好的部分）。场景化之后**重来的是那一场**，成本和命中率都完全不同。
3. **检索的天然边界**：场景自带「谁在场、在哪、干什么、要什么效果」，这就是检索的查询条件。**没有场景级分解，检索层就没有精准的 query。**

这三件事必须一起做——**单独做检索（拿什么当 query？）、单独做场景化（每场景还是全量灌？）都不成立。**

下面按「层」组织，共 9 个方向、43 个可决策项。**§1-§3 是主干（必须做），§4-§6 是配套，§7-§9 是加固与扩展。**

## 1. 事实层：从「背景知识库」升级为「可检索的真相系统」

现状：`entities` / `facts`（带 `valid_from` / `valid_until` 时序）/ `relationships` / `foreshadowings`（四态）/ `writing_motifs`（桥段台账）/ `chapter_states`（章末契约）。**这套模型本身设计得不错，问题在于「喂给模型的方式」。**

### 1.1 检索式注入（🔴 最高优先级）

| 项 | 内容 |
|---|---|
| **现状** | `pipeline/chapter.py` 组装 31 个块，全部 `format` 进一次草稿 prompt。`grep` 全仓无 embedding/vector，唯一检索是 `api/search.py` 的 FTS5+bm25（给用户搜正文用）。 |
| **好消息** | **`alembic/versions/0008` 已经建好了 `fts_facts` / `fts_entities` / `fts_foreshadowings` / `fts_chapters` / `fts_outlines` 五张虚拟表 + 完整触发器，且用 `tokenize='trigram'`（中文友好）。** 检索层的地基已经在了，只是没给模型用。 |
| **推荐方案** | **两阶段检索（粗召回 + 精排），MVP 不引入向量库：**<br>① **结构化过滤（零成本、最准）**：按本章出场人物 → `facts.entity_id IN (...)`；按章号 → `valid_from ≤ N AND (valid_until IS NULL OR valid_until > N)`；按场景地点 → `fact_type='location'`；按伏笔状态 → `status='planted' AND expected_payoff_chapter ≤ N+window`。<br>② **FTS5 补召回**：对场景 beat 文本做 `MATCH`，用 `bm25()` 排序取 top-k，捞结构化过滤覆盖不到的（如"暗示玉佩存在但没明写"的段落）。<br>③ **精排（可选，二期）**：用一个极便宜的小模型调用对 30-50 条候选打相关性分，取 top-8~12。**这一步是"检索质量"的分水岭**，但可以后上。<br>④ **预算化装配**：给每个块设 token 上限，按「硬约束 > 本章相关 > 全书背景」的优先级装，装不下就砍背景。 |
| **备选方案** | A. 直接上向量库（`sqlite-vec` + 本地 embedding）：召回质量更好，但要多维护一个 embedding 流水线（新章要同步 embed），且事实条目短、语义检索优势不明显。**建议二期作为 FTS5 的补充而非替代**。<br>B. 用 LLM 做「查询改写 + 相关性筛选」：把 31 个块丢给模型让它挑。**不推荐——成本更高、且引入了不确定性。** |
| **预期收益** | 草稿 prompt 实际注入从 31 块降到 ~10 块；模型的注意力从"读说明书"回到"写故事"；顺带降 token 成本。**这是治白水最直接的一刀。** |
| **代价** | 新增 `engines/retrieval/` 模块 + 装配器改造；需要一次 A/B 评测验证（`evals` 底座现成）。 |
| **待决** | ① 精排用 LLM 还是纯 bm25？② 是否同步给门禁/定稿也上检索（推荐：**门禁不上**，门禁需要看全量事实才能发现矛盾）？ |

### 1.2 事实抽取从「章末批量」改为「场景尾增量」

| 项 | 内容 |
|---|---|
| **现状** | `extract_and_apply()` 在整章写完后跑一次，抽出全部事实写回圣经。 |
| **问题** | ① 一次抽一章的全部事实，prompt 长、容易漏抽（`facts_extracted ≥ 30` 就是因为漏抽很快掉下来）；② 场景化之后，**场景写完了事实就定了，没必要等整章**；③ 章被隔离（quarantined）时整章事实都不入库，但其中**大部分事实是对的**。 |
| **推荐方案** | 场景尾增量抽取：每个场景写完立刻抽该场景的事实（调用小、上下文聚焦、准确率高）。整章结束时再做一次「合并校验」，只处理跨场景的事实冲突（如场景 1 说剑断了、场景 3 还在用）。**顺带解决隔离粒度问题**：隔离只针对冲突事实，不再整体废弃。 |
| **代价** | 抽取调用数从 1 次/章变成 N 次/章（N≈3-5），但每次输入短得多，**总 token 未必上升**（短输入 + 小模型）。 |
| **待决** | 增量抽取的冲突合并策略：遇到矛盾是「以新为准」还是「标记待人工」？ |

### 1.3 伏笔从「到期提醒」升级为「伏笔日程编排」

| 项 | 内容 |
|---|---|
| **现状** | `ForeshadowScheduler.reminder_block()` 只在伏笔临近/逾期时把 `[⏰临近] xxx` 塞进 prompt。蓝图 prompt 里有"全书 3-5 条主要伏笔，注明埋设/回收区间"，**但没有把「回收」当作硬承诺去排程**。 |
| **问题** | 这是全行业最普遍的病：**模型爱埋伏笔、不爱收**。现在系统只是"提醒"，模型可以选择无视——到了第 80 章你会有一堆悬空线索。 |
| **推荐方案**（借鉴 InkOS 的 `hookAgenda` + `evaluateHookAdmission`）**伏笔三件套**：<br>① **准入控制（写前）**：新增伏笔时必须说明「预期回收章 + 回收方式」，且**限制同时活跃的伏笔数**（如 major ≤ 5 / minor ≤ 15）。超限就拒绝新增（或在 prompt 里明确禁止"再埋"）。<br>② **日程排程（写前）**：章蓝图生成时，系统先算出「这一章应该推进/回收哪几条」，**作为硬性任务写进蓝图**（不是提醒，是"本章必须回收 X"）。<br>③ **健康度审计（写后）**：定期算「伏笔债务」= 活跃数 / 回收率 / 平均悬空章数，超标时**主动要求后续章腾出回收位**。 |
| **备选** | 保守做法：只做 ②（排程），准入和审计后置。 |
| **待决** | 活跃伏笔数上限设多少？（我的建议：按体量动态——每 20 章允许新增 3 条 major） |

### 1.4 读者认知状态（新概念，🔴 强烈建议）

| 项 | 内容 |
|---|---|
| **现状** | 有 `Entity.base_profile`（角色知道什么），但**没有"读者在第 N 章知道什么"这个维度**。 |
| **问题** | 这是「悬念」和「反转」的技术基础。现在系统无法回答：*这个信息，读者现在知道了吗？* 于是「认知颠覆」只能靠 prompt 喊"要有个推翻读者判断的时刻"——**但系统自己不知道读者当前站在哪，怎么可能设计好颠覆？** |
| **推荐方案**（借鉴 Goink 的「读者认知」维度）**引入「读者认知集」**：<br>每条信息记 `{内容, 首次披露章, 披露方式（明写/暗示/未披露）}`。<br>用途一：**反转设计**——转折章生成前，系统列出「读者当前相信 A、真相是 B」，注入 prompt，让模型知道要掀翻什么。<br>用途二：**悬念管理**——避免"读者早就猜到了"（信息给太多）或"读者完全没头绪"（给太少）。<br>用途三：**与事实层区分**——角色知道 ≠ 读者知道，这个差集才是戏剧张力的来源。 |
| **代价** | 新增一张表 + 抽取时多一个维度；需要与 `facts` 区分（`facts` = 世界真相，`reader_knowledge` = 读者已知）。 |
| **待决** | 抽取"读者认知"的可靠性存疑（LLM 判"读者知道了吗"主观）。**建议先做成 advisory（提示不阻断）**，看数据质量再决定是否硬化。 |

### 1.5 事实的「重要度传播」与「失效传播」

| 项 | 内容 |
|---|---|
| **现状** | `Fact.importance` 有 critical/major/minor；`valid_until` 支持失效。 |
| **问题** | ① 重要度是抽取时一次性打的分，**不会传播**——一个 critical 事实作废，依赖它的下游事实（关系、伏笔）不会自动标记复核；② 编辑改了某条事实，**没人知道哪些章引用过它**。 |
| **推荐方案** | ① **引用追踪**：事实入库时记录「由哪一章产生、被哪几章的哪些段落消费过」（检索层天然能提供这个数据）。② **失效传播**：一条事实 `valid_until` 被改动时，反查消费方，生成「受影响段落清单」交给级联引擎——**这正好接上已有的 `setting_cascade`**（设定级级联已经能扫全书受影响章，缺的正是"哪条事实影响哪几章"的索引）。 |
| **代价** | 中等。检索层建成后，这是"顺手多存一个消费日志"的事。 |
| **待决** | 是否值得为它新增存储？（替代：每次现算，慢但不占空间） |
| **✅ 已落地（2026-09-10）** | **新增存储（不现算）**——现算是 O(章数×事实数)，一本 100 章的书每次编辑扫描几万条事实，交互上不可接受。<br>· 表 `fact_usages`（`app/db/models/fact_usage.py`；迁移 `b7e4f2a91c58`；`migrate.py::_add_fact_usage_table` 幂等兜底），索引 `(fact_id, chapter_number)` 与 `(project_id, chapter_number)`，外键 `fact_id→facts` / `scene_id→scenes` 均 CASCADE/SET NULL。<br>· 引擎 `app/engines/consistency/fact_ledger.py`：写侧 `record_usages`(幂等,同键累加 `times`，**循环内 add 后立即 flush**——否则同一 Session 连记两次会看到重复行) / `record_retrieval` / `record_extract_hits` / `forget_chapter`；读侧 `usages_of` / `writeback_map`；失效侧 `invalidate_fact`(支持 `dry_run`) / `render_invalidation_report`。<br>· **两条消费来源**：① `scene_write.write_scene` 检索注入时记 `source=retrieval`（**重写路径不记**——那条 prompt 里没有 facts_block，模型没看到，记了是假账）；② `chapter_maintenance.apply_chapter_tail` 抽取后在新章正文里字面命中旧事实记 `source=extract`（弱信号，`_probe_phrase` 取最长分句，长度+占比双门槛防"重伤"这类短事实满地误命中）。<br>· **失效传播接上级联**：`invalidate_fact` 反查「失效点之后仍引用过它」的章，按「已写正文 vs 未写」分类（未写的生成时自然读到新事实，不用人工复核），交给用户/级联引擎。`cascade/regenerate.py` 在大纲重生成标 `stale` 时调 `forget_chapter` 清掉该章旧日志（否则下次失效传播会误报）。<br>· **体检报告**：`/audit-report` 新增 `fact_usage` 段（`editorial.py::fact_usage_section`）——悬空 critical 事实（写在圣经里从没进过正文）+ 无据章（已成文却零引用记录），前端 `AuditPanel` 已展示。 |

## 2. 生成层：从「章级单发」升级为「场景级编排」

### 2.1 场景级生成（🔴 核心）

| 项 | 内容 |
|---|---|
| **现状** | `beats`（场景节拍）已经在蓝图层产出，`_beats_block()` 把它渲染成"施工清单"塞进 prompt——**但它是建议，模型可以无视**。整章一次生成 3000 字。 |
| **推荐方案** | **把 `beats` 升格为执行单元**，每章按 beats 串行生成：<br>① **场景规划（已有，需强化）**：蓝图已给 beats，但太粗（一句话）。建议**新增"场景卡"结构**：`{场景序号, 地点, 在场人物, 视角人物, 场景目标, 冲突/张力点, 情绪基调, 预计字数, 与前场景的衔接方式, 出场道具}`。<br>② **逐场景生成**：每次只带「本场场景卡 + 本场相关事实（走 §1.1 检索）+ 上一场的末尾原文（语感衔接）+ 全局风格锚」。<br>③ **场景尾处理**：本场写完立刻做 §1.2 增量抽取 + 本场质量判定（见 §2.2）。<br>④ **章末合稿**：所有场景拼完后做**一次"接缝处理"**（只处理场景之间的过渡段，不做整章重写）+ 全章级一致性校验。 |
| **关键设计**：**"放开写"和"压住写"必须在场景卡层面就分开**。<br>场景卡带 `情绪基调` + `张力级别`（如 `爆发/高涨/紧绷/平缓/压抑`），生成时按级别用不同的指令集——**高潮场景只带"放开写"的指令，压抑场景只带"压住写"的指令**，同一段 prompt 里两个矛盾指令的问题从根上消失。 |
| **备选方案** | A. **两段式**（粗粒度）：把章拆成 2-3 个"幕"，每幕一次调用。**成本低、收益大半**，可作为过渡。<br>B. **并行场景生成**：场景之间无依赖时可并行（同一章内场景通常有顺序依赖，收益有限；但**跨章并行**可行）。<br>C. 保持单发但加强 beats 约束（如要求模型按 beat 分段输出 JSON）：**不推荐**——约束输出格式会伤害文笔。 |
| **代价** | 生成调用从 2 次/章 → 2+N 次/章（N≈3-5）；但**回炉成本大幅下降**（只重写坏的场景），总成本上升约 30-60%，在"可翻倍"的预算内。 |
| **待决** | ① 场景卡由谁生成——蓝图阶段一次出全章场景卡，还是生成时按需展开？（推荐：蓝图阶段，因为场景卡需要全书视角）<br>② 场景之间的"钩子衔接"由谁保证——上一场的末尾自动成为下一场的输入，还是显式生成"过渡句"？ |

### 2.2 场景级验收（🔴 与 2.1 配套，缺它就没意义）

| 项 | 内容 |
|---|---|
| **现状** | 验收只有章级：一致性门禁（blocker）+ 主审四维（LLM 自评）。升级到场景级后，**需要场景级的验收标准**。 |
| **推荐方案** | **场景级验收分两类，必须区分确定性 vs 主观**：<br>**A. 确定性验收（纯规则，零 LLM，可靠）**：<br>&nbsp;&nbsp;- 场景卡的要求是否落实（场景目标提到了吗？在场人物都出现吗？道具用了吗？）<br>&nbsp;&nbsp;- 张力曲线是否成立（句长节奏、对白密度、段落长短变化——`polish/ai_flavor.py` 已有这套统计）<br>&nbsp;&nbsp;- 情绪基调是否匹配（用词倾向统计）<br>**B. 主观验收（LLM 判，仅 advisory）**：<br>&nbsp;&nbsp;- "这一场的场景目标达成了吗？""有没有让读者想往下看？"<br>&nbsp;&nbsp;- **只作提示，不触发重写**——LLM 判"好不好"不可靠（我在 `docs/14` 里已经指出） |
| **重写策略** | 确定性验收不达标 → **只重写这一场**（带具体意见）。主观验收不达标 → 标记给用户看，**不自动烧钱**。 |
| **待决** | 场景重写封顶几轮？（推荐：1 轮。第二轮大概率同样结果——这个项目已有"prose 6→6→6 死锁"的实测教训，代码里 `stalled_dims` 就是为它写的） |

### 2.3 章内张力曲线（🔴 你的核心诉求，现在完全缺失）

| 项 | 内容 |
|---|---|
| **现状** | 只有"本章戏核"+"情绪基调"两个标量字段（今天刚加的），以及一句"章内必须有起落"。**没有曲线，只有点。** |
| **问题** | "该精彩时精彩、该压抑时压抑"——**这是曲线问题不是点问题**。一个"高潮章"不是全章高潮，是**蓄力 → 释放**；一个"压抑章"也不是全程压抑，是**压抑中藏着不安的暗涌**。现在系统无法表达"第 3 场爆发、第 5 场冷下来"。 |
| **推荐方案** | **在蓝图/场景卡层面引入显式的张力曲线**：<br>① 每个场景卡带 `张力值`（1-5）；<br>② 章级校验：**张力序列不能是平线**（如 `[3,3,3,3]` 直接判不合格），必须有起伏、且落点符合章的定位（高潮章张力峰值应在后段）；<br>③ **全书级的节奏曲线**（见 §3.2）。 |
| **这是"白水"的正面解法** | 之前靠 prompt 喊"要有落差"是**请求**；现在是**结构约束**——张力序列平了，系统会要求重排，模型没有"平均用力"的选项。 |
| **待决** | 张力值谁来定？（推荐：蓝图阶段 LLM 定 + 用户可改，落在场景卡上） |

### 2.4 编排从「600 行 while 循环」改为「显式阶段管线」

| 项 | 内容 |
|---|---|
| **现状** | `generate_chapter()` 952 行文件、~600 行单函数，内含一个跨 190 行的 `while True` 回炉循环，混合了门禁、精修、止损、落库、章后链路。 |
| **推荐方案** | 拆成**显式的阶段管线**，每个阶段是一个有名字、可单测、可跳过的对象：<br>`PreflightOp → ScenePlannerOp → SceneWriterOp(×N) → SeamOp → GateOp → ReviewOp → GuardOp → DeaiOp → PersistOp → ExtractOp`<br>用统一的 `PipelineContext` 传递状态，每个 Op 声明「前置条件 / 产出 / 失败策略（重试/降级/中止）」。<br>**为什么是重构的前提**：任何新增阶段（场景化、检索、新验收）现在都只能往那个 while 循环里插代码；拆完之后每个新能力是一个独立 Op。**这一步必须在 §2.1 之前做。** |
| **备选** | 保持单函数，只做「提取子函数」的浅重构——**不推荐**，治标不治本。 |
| **代价** | 纯重构，无行为变化，测试可以先行保护（现有 1,120 个测试正好当安全网）。 |

### 2.5 多模型策略：按「角色」而不是按「任务类型」分配

| 项 | 内容 |
|---|---|
| **现状** | `_TASK_TIER` 把任务映射到 `FAST/QUALITY/REVIEW` 三档；**REVIEW 档未配置时回落 QUALITY**——即写手和审校可能是同一个模型。 |
| **推荐方案**（借鉴 InkOS 的 per-agent 模型分配）**显式区分创作与验收的模型**：<br>① **写手（Writer）**：文笔优先，可用更强的模型（成本高但只调用 N 次）；<br>② **验收（Auditor）**：**必须与写手不同模型**——LLM-as-judge 的同模型自审会放大乐观偏差，这是 `docs/14` 已经点出的问题；<br>③ **抽取/记账（Observer）**：便宜快速的小模型即可（这类任务不需要文笔）；<br>④ **检索精排（Ranker）**：最便宜的模型。 |
| **关键改进** | **首次开书时主动引导用户配置**："建议为审校配置一个不同的模型"，而不是沉默回落。 |
| **待决** | 是否强制（模型相同就警告）还是仅提示？ |

### 2.6 生成过程的「可干预」

| 项 | 内容 |
|---|---|
| **现状** | 生成是一个黑盒长任务，中途只能看进度文字，不能干预。 |
| **推荐方案** | 场景化天然带来可干预点：**每写完一个场景就暂停给用户看**（可选，默认自动连写）。用户可以在第 2 场写完时说"这场太拖了，重写"，**而不是等整章写完**。 |
| **备选** | 「先出场景纲要 → 用户确认 → 再写正文」的两段式（更安全，但多一次交互）。 |
| **待决** | 默认全自动还是每场确认？（推荐：默认全自动，提供"逐场确认"开关） |

## 3. 蓝图层：从「章级规划」升级为「全书节奏编排」

### 3.1 场景卡（🔴 §2.1 的前提）

见 §2.1①。需新增字段（在 `outlines` 或新建 `scenes` 表）：
`场景序号 / 地点 / 在场人物 / 视角人物 / 场景目标 / 冲突点 / 情绪基调 / 张力值 / 预计字数 / 衔接方式 / 出场道具`。

**待决（重要）**：场景存 `outlines` 的 JSON 列，还是**新建 `scenes` 表**？
- JSON 列：改动小，但无法被检索层按场景查询、无法单独版本化。
- **独立表：推荐**——场景成了真正的生成单元，就应该有独立的身份（可单独版本化、可单独标记状态、可被检索）。
- **这是本方案里最影响长期形态的一个决策，建议你重点看。**

### 3.2 全书节奏曲线（🔴 呼应 §2.3）

| 项 | 内容 |
|---|---|
| **现状** | 全书级的节奏只体现在"章节定位"（铺垫/转折/高潮/结局）标签上。**没有密度曲线、没有爽点分布。** `docs/14` 里提到的"事后全书体检"也只是一次性检查，不是编排。 |
| **推荐方案** | **卷/弧级的节奏蓝图**：<br>① 每卷定义「张力目标曲线」（如"前 1/3 蓄力、中段两个小高潮、卷末大爆"）；<br>② 章节的张力目标**必须服从卷的目标**（现在章的情绪基调是孤立的，不知道自己在卷里的位置）；<br>③ **爽点/情绪密度排程**：明确"每 N 章必须有一个读者满足点"，作为蓝图的硬约束。 |
| **为什么要做** | 网文/长篇的留存靠的是**节奏**，不是单章质量。现在系统每章都可能"工整"，但整体是平线——**这是读者弃书的真正原因**（比 AI 味更致命）。 |
| **待决** | 节奏曲线用"张力值"单维，还是拆成「张力 / 情绪强度 / 信息密度」三维？（推荐先单维，跑通再加） |

### 3.3 蓝图与正文的「双向校验」

| 项 | 内容 |
|---|---|
| **现状** | 有 `is_stale`（蓝图改了标记正文失配）、有级联重生成。 |
| **问题** | 只有单向（蓝图→正文）。**正文写歪了（没按蓝图写）不会反馈到蓝图**。 |
| **推荐方案** | 场景验收时检测"场景目标达成度"，未达成时**要么重写场景、要么回头修场景卡**（模型写得比蓝图好时，允许蓝图让步）。 |
| **待决** | 是否允许"正文优先、蓝图跟随"？（推荐：允许，但需用户确认） |

### 4.3 「AI 味」从「检测」升级为「指纹级风格约束」

| 项 | 内容 |
|---|---|
| **现状** | 已有 9 类规则加权 + 自愈闭环，**这块是全项目最深的**。但仍是"检测-修正"，是**负向**的。 |

### 5.3 改编质量验收（新）

改编目前**完全没有验收**。推荐引入改编专属的确定性指标：
- **保真度**：原著的 key facts 在改编稿里的覆盖率（对照 §5.1 的事实清单）
- **取舍合理性**：`adapt_note` 里声明的取舍，是否真的落地
- **独立可读性**：不看原著能不能看懂（LLM 判，advisory）

| 决策 | 结论 |
| --- | --- |
| **✅ 已落地（2026-09-10）** | 新建 `app/engines/adapt_audit.py`（保真度核对，**零 LLM、确定性**）+ `app/engines/adapt_extract.py`（把剧本正文 / 漫剧台词摊平成可比对文本）。<br>· **保真度**：原著 critical/major 事实在改编稿里的覆盖率。比对不看措辞看**关键词**——事实内容切成字面短语（长短语优先，`MIN_PHRASE_CHARS=4` 以下丢弃，上限 6 条），改编稿命中任一即算保住。**刻意不做同义/模糊匹配**：虚报「保住了」比虚报「丢了」危害大得多（前者让人不去查）。这是**有偏保守**的估计。<br>· **取舍声明核对**：`adapt_note` 里出现的事实关键词，若声明「保留」而稿里没有、或声明「删/略去」而稿里仍在，都报为人看的**不一致**。关键词取候选短语而非 `content[:12]` 裸切（裸切含标点，声明里永远不逐字出现，比对恒假——踩过）。<br>· **覆盖断点** `gaps`：按章核对，哪几章一条关键事实都没落地。<br>· **短稿不报 0%**：可比对文本 `< MIN_ADAPT_CHARS(120)` = 还没写，报「未评估」（`facts_total=0`、`render=""`），不拿 0% 骗人。<br>· **advisory 语义（关键）**：只产报告、**不设卡口、不改任何生成行为**。理由是事实抽取本身有噪声，拿有噪输入硬卡改编会误杀好稿；报告给人看不花钱。<br>· 两条端点：`GET /api/projects/{pid}/adapt-fidelity`（剧本线，可选 `script_id`，默认取最近由本项目改编的剧本）、`GET /api/projects/{pid}/drama/adapt-fidelity`（漫剧线，按各集 `source_chapters` **并集**限定取材章范围）。<br>· 新增 `tests/test_adapt_audit.py` 19 例 + `tests/test_adapt_fidelity_api.py` 8 例（含归属隔离、无产物 404、未评估语义、note 不一致浮出）。 |

**未做而故意留的**：独立可读性（第三项）仍是 LLM 判，本轮不动——它需要付费调用，且与 §7.2 压测同期做更划算。

## 6. 数据与状态层

### 6.1 从「双轨迁移」改为「单一真相源」

现状：Alembic 17 版 + `migrate.py` 手写幂等补列 + `baseline_schema/` + `evals/fixtures.py::OUTLINE_FIELDS` + 前端 `api.ts`——改一个字段要同步 **9 处**（已写进项目记忆）。

## 7. 可验证性与对外证明

### 7.1 评测底座升级为「三条轨」

| 轨 | 内容 | 何时跑 |
|---|---|---|
| **A. 确定性轨** | AI 味、复读、篇幅比、blobker 生成逻辑、prompt 指纹变更 | **mock LLM，进 CI**，每次 PR |
| **B. 质量轨** | 真实 LLM 跑黄金样本，出对比表 | 改 prompt 时手动（低峰时段） |
| **C. 判别力轨** | **mutation test**：故意改坏 prompt，验证指标确实下降 | 每次改评测体系后 |

**现在缺的是 A 和 C。** A 能进 CI（不花钱），C 能回答"这套评测到底拦不拦得住"——**没做过 C，门槛本身也是未经验证的**。

| 轨 | 状态 |
| --- | --- |
| **A. 确定性轨** | **✅ 已落地（2026-09-10）**：新增 `app/evals/deterministic.py` + CLI `python -m app.evals deterministic`。对既有正文样本（`backend/evals_corpus/`，10 章正式基线落盘正文）算确定性指标并与门槛比对，**不调 LLM、零成本**，已进 CI（`.github/workflows/ci.yml` 的 `evals-deterministic` job）。设计要点：**门槛复用 `thresholds.py`，不另造一把尺子**——两轨（质量轨现场生成 / 确定性轨既有样本）的区别只在「正文从哪来」，同一句话在两轨里含义相同。门禁只判本轨**负责**的指标（`DETERMINISTIC_OWNED`：AI 味均值 / 章内复读 / 篇幅比），质量轨独有的项（主审达标率、blocker 数、事实抽取数）在本轨缺席属正常，不判违规（否则 CI 恒红——实测踩过）。**空样本判失败**而非通过。 |
| **B. 质量轨** | ✅ 已有（`run` / `compare` / `gate` / `resume` / `trend`），低峰手动跑，要 key。 |
| **C. 判别力轨** | **✅ 已落地（2026-09-10）**：新增 `app/evals/mutation.py` + CLI `python -m app.evals mutation`。**故意写坏正文**（复读 / AI 味套话 / 篇幅崩 / 灌水放大），验证确定性指标**确实会掉**——回答此前从没人问过的「这套评测到底拦不拦得住退化」。判据取**相对关系**（退化样本 vs 基准），不写死绝对值（绝对值随模型漂移，相对关系才是尺子有效性的稳定证据）。当前 **4/4 种退化全检出**，已进 CI。 |

## 12. 一句话总结

**现在的系统把「不出错」做到了开源顶尖，但「好看」只分到了 2 次调用的预算。**

下一版的全部工作可以归结为一句话：**把「章」降级为容器，把「场景」升格为生成单元，让每个场景只带它需要的事实、只收到一个明确的情绪指令、只被验收一次。**

—— 这件事做完，"该精彩时精彩、该压抑时压抑"不再是一句 prompt 里的请求，而是**架构本身的保证**。
