# 17 - 生成质量线上观测方案（2026-09-11）

> 背景：上线后的生成质量问题目前零归因通道（无反馈端点、无指标聚合）。
> 离线评测三轨回答「prompt 改动有没有变差」，本方案回答「**真实用户觉得哪里差、和哪类信号相关**」。
> 纪律约束：监控是观测不是特性，不碰生成 prompt/编排（与制片工坊冻结拍板兼容）；零 LLM 成本。

## 一、现状盘点：信号已在库里躺着，只差聚合

| 信号 | 落点 | 现状 |
|---|---|---|
| 上下文截断 | `llm_usage.truncated`（布尔）+ `finish_reason` | ✅ 已落库，无聚合 |
| token/成本 | `llm_usage.prompt_tokens/completion_tokens/user_id/model` | ✅ 已落库，无聚合 |
| 门禁/主审回炉 | `chapter.review_snapshot`(JSON) → `rework_log[].trigger`(gate/review/**gate_degraded**) | ✅ 已落库，无聚合 |
| 质量问题明细 | `chapter_issues`(source/severity/issue_type/status) | ✅ 已落库，无聚合 |
| 摘要抽取失败 | `chapter_states.extract_status/extract_error` | ✅ 已落库，无聚合 |
| 响应耗时 | `llm_usage` **无 duration 字段**（`app/llm/base.py` 无计时） | ❌ 缺 |
| 用户反馈 | **无表无端点无 UI** | ❌ 缺 |

## 二、分期实施

### M1：聚合端点 + admin 视图（约半天，零迁移零新表）

**后端** `app/api/admin.py` 新增 `GET /api/admin/quality-overview?days=30`，一次查询聚合四路：

1. **截断率**：`llm_usage` 按 model/按天 → truncated 占比、finish_reason=length 占比；
2. **回炉画像**：解析 `review_snapshot.rework_log` → trigger 分布（gate / review / gate_degraded 隔离次数）、平均回炉轮数、连续复现止损次数；
3. **问题分布**：`chapter_issues` 按 issue_type × severity × status；open 挂起数；
4. **体量对照**：每章平均 token、每章字数分布（超标/不达标占比）。

**前端** `AdminPage` 加一张「生成质量」卡：截断率、降级隔离数、回炉轮数分布、问题类型 TopN。

**验收**：对黄金库 po_feng_ji 跑一轮生成后，聚合数字与手工 SQL 对得上；端点测试走隔离内存库。

### M1.5：补响应耗时（约半小时，一次小迁移）

`llm_usage` 加 `duration_ms INTEGER`；`app/llm/base.py` 写入点单点改造（perf_counter 包住调用）；迁移按常规 alembic 流程（新列 + `migrate.py` 幂等补列挂进 `run_migrations()`）。

### M2：用户反馈闭环（约一天，一张新表）

**表** `chapter_feedback`：`chapter_id / user_id / rating(good|bad) / categories(JSON 数组) / comment(Text) / content_hash`（对齐 chapter_issues 的 content_hash 口径，改稿后旧反馈可判失效）。

**差评四桶**（对应已知四类风险，埋点前先想清楚要回答什么问题）：
- `style_flavor` 文风 AI 味
- `fact_error` 事实/设定错误
- `pacing` 节奏平淡/失控
- `format_trunc` 格式问题/截断感

**端点**：`POST /api/chapters/{id}/feedback`（upsert，一人一章一条可改判）、`GET` 回显自己的反馈。

**UI**：章节阅读/完成态视图挂 👍/👎，点 👎 展开四桶多选 + 选填备注。**放在用户「读完的地方」，不是编辑器里。**

**聚合**：M1 端点补第五路——差评分布，并做**交叉归因**：差评章的 truncated 率 / 降级率 / 回炉轮数 vs 全体均值。这就是「没监控以为是模型能力问题，有监控发现是截断」的那一步。

**迁移注意**：新表走 alembic 新迁移 + `Base.metadata`（create_all 兜底自动建）；不走 outline 字段同步清单（那是蓝图字段专用）。

## 三、明确不做的

- 不接外部 APM/监控服务（数据敏感，库内自聚合够用）；
- 不做实时告警（当前量级 weekly 看一眼足够，等有数据再说）；
- 不给制片六线加反馈（冻结期，小说主线优先）。

## 四、顺序与理由

```
M1(聚合既有信号) → M1.5(耗时) → M2(反馈闭环)
```

先 M1 的理由：零迁移、半天见效，且 M2 的交叉归因直接复用 M1 的四路聚合。
全部做完 ≈ 2 天，均在低峰期、零 LLM 成本。做完后，检索式注入/场景级生成这两个大改造上线时，就有「真实用户是否变好」的判据了。
