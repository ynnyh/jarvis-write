# 开书到成稿全链路：深度调研与「深聊一次、拍板两回」改造方案

> 状态：方案稿，待作者拍板
> 日期：2026-09-26（v2 重写：补 14 项目深调研，方案具体化）
> 关联：08-章节生产流水线、09-新建小说向导、19-核心梗为纲、20-订单制改造、21-Skill内置方案
> 起因：作者实测反馈——「沟通是对的，但事无巨细有点过。还是需要多聊，尽量减少抽卡；抽卡时要尽量多的确认细节，而不是给几个字的方向就去抽。过程中可以给几个方向并给出推荐，但要用户确认的不要太多。」

---

## 0. 结论先行

**「确认细节」和「用户拍板」是两件事，必须解耦。**

- 抽卡率的根源是**生成时已确认细节的密度**——细节托底越厚，生成越不靠赌；
- 但细节的确认劳动应该由 **AI 出方案、用户点选/默许** 完成，而不是用户逐项填写、逐层拍板；
- 全链用户显式拍板收敛到 **2 次**（整书方案拍板 + 试读前三章校准），其余细节全部走「AI 定 + 透明展示 + 随时可改」。

方案一句话：**开哪种书（📖 短故事 / 📚 连载，模式级分叉前置）→ 三问定纲（全候选带推荐）→ 整书方案 ×3（点选一套、一句话定向修订）→ 拍板开跑（连载一枪到黄金三章 / 短故事一枪到全文）→ 试读校准 → 连载零拍板（细节台账托底生成）**。

## 1. 现状回顾：难在哪（代码实测）

五步主线：`想法 → 简介对谈(L0) → 概念打磨(L1) → 配置(梗卡必填) → 点火(架构闸门L2→骨架墙→铺章) → 工作台(六单L5→正文L6→审核)`

四个结构性问题：

1. **同一信息确认三遍**：订单拍板→概念六字段过目→总检+梗卡必填，主角/困境/世界观过目三次。
2. **访谈制把用户当需求方**：`prompts/inspire.py:203-208` 规定策划逐格问、「没聊定写『未定』、作者没明说的不许替 TA 定」——AI 被禁止发挥细节，4-6 轮起步；且每出新草稿自动回锁（`brief.py:126`），拍板永远追着草稿跑。
3. **拍板粒度跟着内部工序走**：雪花四层、骨架逐段都是流水线内部中间表示，用户被迫逐层拍板自己不消费的东西。
4. **门槛链事实存在**：3 道后端硬门（订单409/架构链409/铺章400）+ core_seed 默认必停 + 梗卡必填。读到第一章 ≈ 12-16 次刻意交互、3 次强模型等待串行卡在人眼前。
5. **没有「写什么」的模式分叉，规模由 AI 偷偷定**：篇幅藏在配置屏第三页签，`OnboardingFlow.tsx:182-192` 在用户没动过时**自动选中 AI 推荐档**（shapeSug）；四档预设（`onboarding/presets.ts`）最短的「短篇」也是 **20 章 ≈ 6 万字**的连载式管线——**不存在「一次讲完」的短故事形态**，而架构四层/骨架分段/六单对短故事全是杀鸡用牛刀。题材选完后写出来的是什么规模，用户从头到尾没有被问过。

### 2.2 五个可复用的交互范式（带出处）

**范式 A：分层问卷——「必答极少、可选分层、每问三逃生」**（chinese-novelist-skill）
- L1 必答 3 问：题材创意 / 主角设定 / 核心冲突；L2 可选 5 问：世界观 / 叙事视角 / 核心主题 / 读者定位 / 章节数量。
- 每问三个逃生口：**🎲随机生成 / 跳过 / 用默认**。不想答永远有出路。
- 偏好记忆 `user-preferences.json` 跨会话学习（题材/叙事风格/章节倾向），下次少问。

**范式 B：整书方案多套候选 + 定向修订**（Biz Novel Studio、马良、MuMuAINovel）
- 一句灵感 → 系统先生成**多套完整整书方向（含对应摘要组）**，不是逐格问答。
- 不满意时**不整批重来**：可以「持续生成新的」「定向修订某一套方案」「叉出重做某一套的摘要组」——把「满意就确认 / 不满意就重来」拆开。
- 马良同款：设定树一键生成 → 不满意**微调节点** → 黄金三章。

**范式 C：摘要确认制——用日常语言收口，模糊不算确认**（awesome-novel-agent）
- agent 写完设定 → 展示**面向作者的日常语言摘要**（文件清单+要点），结尾话术：「哪里不对直接说；没问题就说『可以』」。
- 模糊回答（「差不多」「你看着办」）→ **视为未确认**，追问具体哪项不确定。
- 「你全权写」= 全自动模式，展示摘要后视为已确认直接推进。

**范式 D：候选-采纳-回执，证据可查**（StoryForge、goink、NovelForge）
- 「正式创作先产出候选，作者确认后写回」；采纳 → 回读 → 验收回执。
- 等待确认期间原文变了 → 旧候选标 stale 拦截，不覆盖新编辑。
- Context Manifest 记录生成用了哪些来源、实际读了什么、缺了什么——结果不好可以**归因**而不是重抽。
- NovelForge 的指令流式：输入要求 → **字段粒度流式填充** → 确认或反馈继续，不整卡重生成。

**范式 E：门禁只对质量，且先自动重写再报人**（天命、chinese-novelist-skill、Biz Novel Studio）
- 天命六道门禁：协议解析/引用校验/一致性校验/未登记实体检测/描写一致性/蓝图出场检查——**全部对准生成质量**，不过不落库，没有一道门是「逼用户表态」。
- chinese-novelist-skill：字数+连贯性自动校验，**不合格自动重写最多 3 轮**，人不参与。
- Biz Novel Studio：蓝图指定登场角色没出场 → 打回重写，而不是问用户怎么办。

### 2.3 共同形态提炼

把做得好的项目拼起来，开书到成稿的最优交互是一条**两拍板主线**：

```
一句灵感（可空，有🎲兜底）
 → [浅访谈] 必答≤3问，全候选制+AI推荐+三逃生（随机/跳过/默认）     ← 范式A
 → [整书方案×3] 完整方案卡，点选一套 + 一句话定向修订（可多轮）      ← 范式B
 → ❶拍板：就写这套（唯一前置硬门）
 → [一枪生成] 概念/设定/骨架/黄金三章全自动，日常语言摘要实时汇报    ← 范式C
 → ❷拍板：试读前三章，满意开连载 / 不满意带话归因重做（局部优先）
 → [连载] 下一章直接写；写后自检门禁不合格自动重写≤N轮才报人        ← 范式E
 → 所有中间产物 = 可看可改可锁的「书档」，改动带 stale 级联          ← 范式D
```

**细节确认量 >> 用户拍板量**：候选点选 = 一次点击批量确认一批细节；AI 默认+透明展示 = 过目即默许；台账 = 全部细节有出处、可追溯、可事后改。抽卡率随细节密度下降，而用户成本不随之上升。

## 3. jarvis-write 改造方案：「深聊一次、拍板两回、细节台账托底」

### 3.1 开书交互剧本（替换现简介对谈）

**屏 0 · 开哪种书**（新增，全链第一问，模式级分叉）：

```
今天想写什么？
┌─────────────────────┐  ┌─────────────────────┐
│ 📖 短故事            │  │ 📚 开书连载           │
│ 一次讲完,3千~2万字    │  │ 短/中/长/连载四档      │
│ 情绪完整,当天出成品   │  │ 长线引擎,持续写下去    │
└─────────────────────┘  └─────────────────────┘
        [🎲 说不清,AI 按我的点子推荐]
```

- 这是**模式分叉不是参数**（awesome-novel-agent 短/长流程、目录、agent 组完全独立且禁止混用；StoryForge 顶部即分「长篇/短篇」入口）：两 种模式后续的灵感引导语、三问内容、方案卡形态、生成管线全不同。
- 连载模式的档位（短 20 章/中 60/长 150/连载 500+）**在此明示选择**：默认高亮 ★AI 推荐档（按点子/偏好推荐），点其他卡即改——从「AI 偷偷选中」改为「明示推荐+用户轻确认」。
- 🎲「说不清」：进灵感一句话 → AI 连模式带档位一起推荐 → 用户确认。
- `project.mode`（short | serial）+ 档位落库，项目卡展示，进偏好记忆。

**屏 A · 灵感**（按模式变引导语）：一句话（可空）+ 流派卡（可跳）+ 🎲随机开一本。短故事问「想讲一个什么瞬间 / 一种什么情绪」；连载问「什么梗能让你写一百章」。

**屏 B · 三问定纲**（新增，替代逐格访谈）：
一次 FAST 调用出「三问卡」，每问 3-4 个具体候选，**AI 首推标 ★ + 一句推荐理由**，底部一个「全部按推荐来」大按钮：
1. **写什么味道**——题材 × 基调（如「都市异闻·冷峻悬疑」/「仙侠·热血逆袭」）
2. **主角是谁**——身份 + 底色 + 想要什么（具体的人，带反差）
3. **最大的坎是什么**——核心困境形态 + 破局反差点

每问三逃生：`🎲换一批` / `自己写` / `跳过（AI 按题材惯例定）`。三问的候选与推荐由**偏好记忆**（global_tendency + dna）驱动，越用越准。第 3 问随模式变：连载问「最大的坎」（长线困境+连载引擎），短故事问「结尾想落在什么感觉上」（结局情绪定调）。

**屏 C · 整书方案 ×3**（核心升级，替代「订单五段」）：
一次 ARCHITECTURE 调用出 **3 套完整整书方案**，每套一张卡（连载方案含推荐档位★，短故事方案换形态：完整故事弧三幕 + 字数档 + 结尾情绪，不含连载引擎）：

```
┌ 方案一《镖箱里的活人》        差异坐标:小人物·生计·燃 ┐
│ 内核：落魄镖师接险镖，箱里藏着通缉的前朝公主……       │
│ 主角：沈铁衣，34岁，信「规矩」不信人心——直到规矩吃了他 │
│ 世界观：清末民初江湖末法时代，武行是最后的体面行当     │
│ 首卷走向：接镖→验箱见人→三方追杀→他把镖送给了自己     │
│ 连载引擎：每一趟镖都是一个局，局局相扣               │
│ 味道：冷峻热血·群像·救赎                            │
└──────── [选这套] [改改再选✎] ────────────────────────┘
```

- **[改改再选]**：输入一句话（「主角换成女性，基调再冷一点」）→ 只重生这张卡（定向修订，不整批重来）。
- **[再来三套]**：可带话（「不要江湖背景」），avoid 防趋同（已有机制）。
- **[就写这套]** → **❶拍板**（`brief_confirmed` 语义迁移为方案拍板，后端 409 硬门保留，全链唯一前置硬门）。
- 想深聊的用户：L2 深聊批次收在「展开更多」（世界观底盘/视角/感情线/连载引擎/红线排斥，每项带默认），以及方案卡的定向修订——深聊入口永远在，但不在必经路上。

### 3.2 设定台账（新增数据模型，细节托底的载体）

拍板的方案展开成**结构化台账**，此后的所有生成细节都往台账里落：

```python
# backend/app/models 新增 project_ledger
project_id | group(kernel|protagonist|world|flavor|engine|redline|naming)
key | value(text)
source: user_picked(点选/改过) | ai_recommended(推荐被采纳) | ai_decided(自动生成)
locked: bool | stale: bool | origin_step | updated_at
```

- **注入**：概念深化/架构/蓝图/正文 prompt 组装时按分组+相关性选条目，标注来源——「作者拍板，严格遵守」vs「AI 所定，可优化但须自洽」。订单注入机制（20 订单制）直接扩展。
- **展示**：工作台「本书档案」面板，分组卡片 + 来源徽标 + 点开即改；改 `kernel/protagonist/world/engine` 组触发下游 stale（现有级联全复用）。
- **锁定语义**：拍板只锁方向组条目（重生成不覆盖）；任何条目用户都可以手动 🔒（骨架段锁的推广）。**拍板从「通行证」变「锁」。**
- **对账**：每章生成后，蓝图「梗兑现」对账（19 核心梗为纲）扩展为「台账兑现」——本章兑现了哪些承诺、动了哪些设定，写进章后摘要，异常才浮出。

### 3.3 生成链路：一枪到黄金三章（连载）/ 一枪到全文（短故事）

**连载模式**，拍板后自动连跑（现信任模式转正为默认，闸门模式保留为精控开关）：

```
方案 → 概念六字段(AI定) → 题材/书名(AI候选自动选) → 梗卡(AI兜底,不再必填)
→ 架构四层(连跑) → 首卷骨架 → 前三章蓝图+正文 → 停:📖 试读前三章
```

**短故事模式**，专用轻管线（架构四层/骨架分段/六单/连写队列全部跳过）：

```
方案 → 情绪核+梗(=梗卡,AI兜底) → 故事弧卡(开场钩子/两三个转折/结尾情绪,一次生成)
→ 按弧分 3-5 拍逐拍成文 → 停:📖 试读全文 → 带话改某一段/重写 → 定稿导出
```

- 短故事同样吃**细节台账**（人物/世界观/语调条目照常注入托底）和**门禁+自动重写**——轻的是管线不是质量。
- 两模式共用：过程流水线卡+日常语言摘要实时汇报（范式 C）；断点续跑（job 机制已有）；中间产物全部落台账/书档，不拦路、不设必填、随时可改。
- 概念屏、配置屏、架构闸门、骨架墙四个界面合并瘦身成「书档预览 + 试读页」。

### 3.4 试读校准（❷拍板，可轻可重）

- 满意 → 「开写下一章」进连载。
- 不满意 → 和策划聊一句，**归因到层级再动手**（反对盲目重抽）：
  - 方向不对（「这不是我想写的」）→ 换方案重来（重来向导已有，从概念/架构重来档）；
  - 开局不对（「前三章太闷」）→ 带话重铺首段骨架 + 重写前三章；
  - 局部不对（「第二章开场不行」）→ 带话重写该章/该场（场景级定点重写已有）。

### 3.5 连载回路（日常，零拍板）

- 「下一章」直接写：prepare（台账+圣经+上章契约+到期伏笔投影，已有）→ compose → **门禁不合格先自动带意见重写 ≤2 轮**，仍不过才弹三选一（新增自动兜底，范式 E）。
- 六单收进「本章想管细一点」高级面板：展开预填单、改完按单写；不展开永不打扰。
- 严格连写审核（approve）保留为项目级开关，默认关。

### 3.6 拍板点对账（改前 → 改后）

| 现在的确认点 | 改后 |
|---|---|

### 4.1 验收指标（P0 埋点先行，上线即量——没有指标等于没闭环）

**线上埋点指标**（方案屏/试读页/生成 job 各埋事件）：

| 指标 | 目标 | 说明 |
|---|---|---|
| 想法屏→方案拍板的用户操作次数 | ≤ 8 次 | 点选/输入各计 1；上线前先采老链路基线对照 |
| 三套内选中率（不点「再来三套」） | ≥ 70% | 方案层命中率的直接度量 |
| 平均定向修订轮次 | ≤ 2 轮 | 超了说明方案差异化不够或推荐不准 |
| 拍板→试读全自动成功率 | ≥ 90% | 一枪链路无人工干预到达试读页 |
| 试读后「方向级重来」率 | ≤ 20% | 换方案/重铺首段占试读校准的比例，局部重写为主才健康 |
| 单本开书到试读的 token 与耗时 | 建基线，不设阈值 | 成本账从这里来，先量再优化 |

**P0 开发期人工验收门**：

- **端到端忠实度**（下一个要去险的假设）：拍板方案 → 一枪 → 前三章，抽 3 本人工对照——三章写的必须是方案里的首卷走向/主角/世界观，不是「另一个故事」。
- **多轮修订不漂移**：同一方案连续 3 轮定向修订后，未要求字段累积变化可忽略。
- **修订边界**：修订要求与方案强冲突（如「连载引擎换成单元剧」）时不静默失真，给可感知的响应。

## 5. 风险与对策

- ~~**最大赌注：整书方案×3 的质量**~~ **已实验去险（2026-09-26，见 §5.1）**：真实模型 6 轮方案 + 2 轮定向修订全部通过——JSON 一次解析 6/6，单轮三套两两相似度 0.055-0.10（差异充分拉开），方案具体度达到选题会水准（具体的人/数字/反差），修订服从度好（只改该改的、连带一致）。遗留两个小修正已并入 P0 落点：修订 prompt 加「未要求修改的字段逐字保留」；方案 prompt 显式约定「方案一直读作者想法、另两套发散」（实验中两轮同输入的方案一收敛到同一主解读，属可用的稳定行为，明示后更可控）。
- **3 套整书方案的 token 成本**：实测单轮输出 1.6-2.1k 字、耗时 8-11s（ARCHITECTURE 档）；定向修订 2-3s、改动量极小。成本与延迟都在可接受范围。
- **方案→下游忠实度**：沿用现有「作者已拍板的开书订单（最高约束）」注入，台账进一步把约束条目化。
- **用户真想深聊怎么办**：L2 深聊批次 + 方案定向修订 + 摘要确认话术（「哪里不对直接说」）三个深聊入口都在，只是不在必经路上——与 awesome-novel-agent 的「你全权写」/追问机制同构。
- **两拍板之间生成跑偏**：试读校准的归因三档确保「重来的粒度永远跟问题走」，不会因为第二章开场不好而重铺全书。

### 5.1 去险实验记录（整书方案×3 + 定向修订）

- 脚本：`backend/scripts/exp_book_plans.py`（可复跑）；结果：`backend/tmp_exp_book_plans_result.md`。
- 环境：spark 容器线上模型配置（ARCHITECTURE 档出方案、FAST 档修订），2026-09-26。
- 用例：一句话灵感×2（同输入测方差）/ 题材无线索×2 / 带红线诉求（女主事业不要系统流）/ 完全没头绪。
- 结果：六轮全部 3 套齐全、JSON 一次解析成功；label 全唯一；题材边界与红线诉求全部遵守（都市悬疑无超自然、女主事业线无系统金手指）。
- 修订实测：「主角换成女性，基调再冷一点」——书名不动、内核只换一个字、人称全翻、味道追加「冷冽」，未要求的情节一字未动；「不要门派修炼体系」——剑宗→铁匠行会全链一致替换（盗剑罪→盗铁罪、剑碑→招牌），未涉及字段不动。
- **实验的边界（如实）**：n=6+2，单模型（线上 ARCHITECTURE 档 deepseek-v4-pro）——够 go/no-go，不是统计结论；修订只测了主角/世界观两类指令，多轮连续修订与强冲突指令未测（列入 4.1 人工验收门）；换 ARCHITECTURE 档模型后需复跑本脚本。
