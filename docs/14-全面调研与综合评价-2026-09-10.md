# jarvis-write 全面调研与综合评价

> 评估日期：2026-09-10 · 代码基线：`main` @ d1b4c72（含当日三项改动）
> 评估方法：全仓代码取证（规模/结构/调用链/门禁）+ 真实测试结果 + 开源同类项目横向调研
> 上一份评估：`docs/11-综合评估与方向建议.md`（2026-09-08，基线 3d4042a / v0.38.0）

---

## 0. 一句话结论

**工程底盘已经是开源同赛道的第一梯队；真正的差距不在"做得少"，而在"生成的那一层太薄"。**

jarvis-write 用两年时间（实际约 8 周）把"包在 LLM 外面的控制层"建成了一个真系统——时序圣经、伏笔四态、大纲级联、设定级级联、去 AI 味量化闭环、覆盖式测试与公约门禁，这些是真的、能跑的、别人没做全的。

但**控制层越厚，生成层越显单薄**：一章 3 千字，系统要花 9~11 次模型调用，其中**只有 2 次是"写"，其余全是"查、审、修、守"**；草稿 prompt 一次注入 **31 个上下文块**，全靠"全量灌"而不是"按需取"；整章**单次成文**，没有场景级分解。

这三点串起来，就是"文绉绉、喝白水"的结构性根因——**系统把绝大部分算力花在了"不要出错"上，而"要好看"只分到两次调用的预算。**

## 3. 核心诊断一：生成架构是「校验厚、创作薄」

这是本次调研最重要的一条，也是你那个模糊的"不够好"的**结构性解释**。

### 3.1 一章要打 9~11 次模型，只有 2 次在创作

`generate_chapter()`（`pipeline/chapter.py:352`）的实际调用清单：

| # | 环节 | 档位 | 性质 |
|---|---|---|---|
| 1 | 写前审核（蓝图 vs 上章契约） | — | 校验 |
| 2 | **草稿** | FAST | **创作** |
| 3 | **定稿** | QUALITY | **创作** |
| 4 | 一致性门禁 | REVIEW | 校验 |
| 5 | 定点修复（可跳过） | REVIEW | 修补 |
| 6 | 校对硬伤自修 | POLISH | 修补 |
| 7 | 主审四维打分 | REVIEW | 校验 |
| 8 | 字数守卫（超标才跑） | POLISH | 修补 |
| 9 | AI 味自愈（超标才跑） | POLISH | 修补 |
| 10 | 章后事实抽取 | QUALITY | 记账 |
| 11 | 章末契约提取 | QUALITY | 记账 |
| 12 | 滚动摘要 + 文风备忘 | SUMMARY | 记账 |

> **创作 : 非创作 ≈ 2 : 9。** 这不是说别的环节没用——它们确实是"不崩"的保险。但**保险买得再多，也不会让一章变得好看**。

### 3.2 草稿 prompt 一次注入 31 个上下文块

`prompts/chapter.py` 的 `CHAPTER_DRAFT_PROMPT` 有 **31 个占位符**：

```
本节蓝图 5 项 · 节拍 · 下章蓝图 · 架构节选 · 滚动摘要 · 近 2 章尾部
上章契约 · 硬约束 · 角色名册 · 资源账本 · 伏笔提醒 · 装置催场
防复读（字面+桥段）· 疲劳词 · 雷区 · 文风块（含 DNA/技法卡/文风范本/备忘）
戏剧任务 · 反AI腔规则 · 字数三档 · 场景数/场景字数 · 重写块
```

**问题不在于"块多"（每块都有理由），而在于注入方式：全量灌，不做相关性检索。**

行业已经有明确结论（2026 年多篇工程复盘都指向同一个点）：

> *"If the instructions become longer than the creative output, the agent spends more tokens reading manuals than writing."* —— 元数据膨胀（metadata bloat）是长文生成的头号隐性杀手。

开源同行的解法都是**检索式注入**：

| 项目 | 解法 |
|---|---|
| **InkOS** | **Composer Agent** 从 7 个真相文件里**按相关性选择**上下文，编译成 `context.json` + `rule-stack.yaml`；SQLite 时序记忆库按相关性 + 时间衰减检索 |
| **Goink** | 本地语义搜索（ONNX Runtime + `sqlite-vec`），查"关于玉佩的线索"连**暗示玉佩存在但没明写**的段落都能召回 |
| **Vela** | 一键导入设定集 → RAG 向量知识库，生成时自动提取相关上下文 |

**我们：`grep` 全仓没有一个 embedding / vector / 语义检索实现。** 唯一的检索是 `api/search.py` 里给"用户搜正文"用的 SQLite FTS5 + bm25——**是给人用的检索，不是给模型用的检索。**

后果：写到第 80 章时，**每一章都要背着全书的所有约束出发**，而真正跟这一章相关的可能只有 15%。模型在冗余信息里找重点，写出来自然平均、平滑、不出格——**这正是白水的配方**。

### 3.3 整章单发，没有场景级分解

当前：`草稿调用` 一次性产出 3000 字整章，`beats`（节拍）只是塞进 prompt 的"施工清单"，模型**可以遵守也可以不遵守**，没有任何结构约束。

开源对照：

| 项目 | 生成编排 |
|---|---|
| **WriteHERE**（EMNLP 2025 oral） | 异质递归规划：把写作拆成**检索/推理/写作**三类子任务，DAG 调度，递归到原子任务。单次可出 4 万字，论文实证优于单发 |
| **InkOS** | `Architect` 独立规划"大纲 / **场景节拍 / 节奏目标**" → `Writer` 只负责散文 |
| **Goink** | 写完一章强制自查（角色变化？伏笔该收？弧线该推？）——**是硬约束不是建议** |

我们的 `beats` 方向是对的（`blueprint` 已经产出 `beats` 数组，`_beats_block()` 已渲染），但**只是文本提示，没有变成"一段一调用"的执行结构**。要在章内实现"该精彩处放开、该压抑处压住"，**逐场景生成 + 场景级验收**是唯一能真正落地的手段——因为"放开"和"压住"是两种不同的指令，塞在同一段 prompt 里必然互相稀释。

### 3.4 小结：三层漏斗的优先级

```
现在：  校验厚（9 次）· 注入全（31 块）· 生成薄（1 发整章）
目标：  校验厚（保留）· 注入准（检索）· 生成厚（逐场景）
        └─ 保留   └─ 改造      └─ 新建
```

**"注入准"和"生成厚"是下一阶段唯一值得重投的方向。** 它们不是加功能，是**换引擎**。

## 4. 核心诊断二：三条改编线的能力落差

你的既定路线是 **小说 → 剧本 → 漫剧**。这条链上每一环的"质量关卡密度"是这样的：

| 关卡 | 小说线 | 剧本线（今日新建） | 漫剧线 | 短片/宣传片 |
|---|:---:|:---:|:---:|:---:|
| 专用引擎层 | ✅ 3,220 行 | ✅ 413 行 | ✅ 3,982 行 | ✅ |
| 素材口径（保头尾/预算/按章平分） | — | ✅ | ✅ | ✅（`adapt.py` 已统一） |
| 书级资产注入（DNA/雷区/偏好） | ✅ | ✅ | ✅ | 部分 |
| 章末交接契约 | ✅ | ✅（今日补） | ✅ | ✗ |
| **格式门禁 + 崩坏重试** | ✅ | ✅（今日补） | ✗ | ✗ |
| **版本快照 / 回退** | ✅ | ✅（今日补） | ✗ | ✗ |
| **一致性校验（对照圣经）** | ✅ | ✗ | ✗ | ✗ |
| **审校打分 / 回炉** | ✅ | ✗ | ✗ | ✗ |
| **去 AI 味闭环** | ✅ | ✗ | ✗ | ✗ |
| 测试覆盖 | 1,134 行门禁测试 | 10 个用例 | 多个 | 少 |

**结论**：小说线是"全关卡"，剧本线今天从"裸奔"补到了"三件套"，**漫剧线（代码量最大）在质量关卡上反而最空**。

这里有个**结构性机会**：剧本和漫剧吃的是同一本书的同一批事实。它们完全可以**继承小说线已有的圣经/伏笔/契约基础设施**，而不是各自重新猜。今天新建的 `engines/adapt.py` 就是这个思路（素材口径统一），下一步应该是**把 `BibleService` 的只读查询能力开放给改编线**——改编时对照"第 N 章时这个角色是什么状态"，而不是只看到一段正文。

## 5. 核心诊断三：验证闭环仍未闭合

`docs/11` 列的 5 条 P0，两天内的实际进展：

| # | 问题 | 状态 | 证据 |
|---|---|---|---|
| 1 | 一致性门禁 LLM 失败 → 静默放行 | ✅ **已修** | `chapter.py:613-628` 降级 → `quarantined` 隔离，不进圣经 |
| 2 | 事实抽取失败 → 静默返回 `{}` | ✅ **已修** | `extractor.py:286` → `degraded_stats`；`chapter_maintenance.py:168-183` 落可见问题（`source=extract`），可一键补抽 |
| 3 | 评测无固化门槛 | 🟡 **做了一半** | `evals/thresholds.py` 门槛表已落地（6 项硬门槛 + `gate` 命令）；**但 CI 里没有评测 job**，因为评测必须真调 LLM，无法在 CI 跑 |
| 4 | 主审四维是自评且默认同模型 | 🟡 **做了一半** | `Task.CONSISTENCY → Tier.REVIEW`，`self_review` 标记已回传前端；**但 REVIEW 档未配置时仍回落 QUALITY 档（=写手同模型）** |
| 5 | 文档"可切 Postgres"不实 | 🟡 **改了一半** | `README.md:250` 已诚实更正；**`README_EN.md:181` / `docs/01-architecture.md:38,51,52` / `backend/README.md:10` 仍是旧说法** |

另外两项 P1 已顺手解决：**外键约束已开**（`db/session.py:48` `PRAGMA foreign_keys=ON`）、**后台任务已落 SQLite**（`jobs.py` 重启后 running>30min 自动标 failed）。

**还缺的三件事**：

1. **门槛进 CI 的可行路径**：把**确定性指标**（AI 味指数、复读、篇幅比、blocker 数）在 mock LLM 下跑——这些不依赖真模型质量，可以固化；真模型部分留给发布前手动跑。现在 `gate` 命令只能手动。
2. **判别力验证（mutation test）**：故意删掉去 AI 味反例段，看指标是否真的下降。**没做过这一步，就无法回答"这套评测到底拦不拦得住"**——门槛本身也是未经验证的。
3. **对外可信度材料**：`docs/12` 的 50 章压测数据（连贯分 8.0~8.3 零衰减、AI 味零漂移、门禁零拦截）**质量很高但只在仓库里**。项目已经有免登录分享链接能力（v0.37），**挂一本真写出来的书比 2000 字功能介绍有说服力一百倍**。

| **jarvis-write** | 开源 · Web+桌面+安卓+Docker | **时序圣经**（事实绑生效区间，可查"第 N 章时角色状态"）+ 伏笔四态 + 桥段台账 | 章级单发 + 章后抽取/契约闭环 + **9~11 次调用里 2 次创作** | LLM 门禁（blocker 分级、定点修复、止损隔离、**隔离而非放行**） | **量化闭环**（9 类规则 + 自愈重写 + 安全阀 + 篇幅守卫） | Docker / 桌面包 / 安卓包 / 源码 |

### 7.2 我们真正站得住的四条

1. **时序故事圣经**：`valid_from/valid_until` 区间过滤 + 事实取代（`bible.py:128-192`）。**能回答"第 N 章时这个角色是什么状态"——这是 InkOS 的"真相文件 + 检索投影"回答不了的。**
2. **大纲级联 + 设定级级联**：改一章大纲 → 规则粗筛 + LLM 精判 → 下游影响分析 → 用户勾选重生成 → 失配标记。`docs/11` 调研时"同类开源一个都没做"，**到今天仍然成立**；`setting_cascade.py`（351 行）把这条从章级推到了设定级。
3. **去 AI 味的工程化程度**：InkOS 是"疲劳词表 + prompt 介入"，**我们是"量化指标 + 定向重写 + 复测 + 没改好自动回退"的闭环**，且有 9 类规则的加权表（`ai_flavor.py`）。这一条我们更深。
4. **工程纪律**：引擎分层门禁、UI 版面门禁、schema 漂移门禁、1,100+ 测试。**开源同赛道没有第二家把架构纪律做成 CI 硬门禁。**

### 7.3 必须承认的四个差距

| 差距 | 严重度 | 说明 |
|---|:---:|---|
| **无检索层** | 🔴 高 | InkOS 有 Composer + SQLite 时序检索，Goink 有本地语义搜索，Vela 有 RAG；我们全量注入 31 块。**这是当前最大的单点差距，且直接造成"白水"。** |
| **无场景级生成** | 🔴 高 | WriteHERE 递归分解、InkOS Architect 独立编排节拍；我们整章单发。 |
| **分发门槛** | 🔴 高 | 人家一条命令；我们 Docker/桌面包/源码三选一。 |
| **数据校验纪律** | 🟡 中 | InkOS 用 Zod"坏数据直接拒绝"；我们已大幅改善（显式降级 + 隔离），但仍是"降级后标记"，不是"拒绝写入"。 |

### 7.4 评测体系的行业坐标

值得对标的公开基准（可用于自证）：

- **EQ-Bench Longform Creative Writing**：8 章 × ~1000 词，LLM 评委按 **world-building / voice / pacing / emotional nuance** 四维打分，另测 degradation / slop / repetition。当前 SOTA ≈ 85~90。
- **Antislop**：量化"AI 套话密度"——**这个口径和我们已有的 AI 味指数是同一类东西**，我们的更细（9 类加权）。
- **ConStory-Bench**（2026）：8k~10k 词长文的**一致性**测试——和我们的 blocker 数指标同源。

> **启示**：我们的确定性指标（AI 味指数、复读、篇幅比、blocker 数）**已经足以拼出一份对外的"健康报告"**，缺的只是把它做成可展示的产物。

## 9. 建议路线（按 ROI 排序）

### 第一档 · 换引擎（下一个大版本的主要内容）

**① 建检索层——"全量注入"改"按相关性注入"** ⭐ 最高 ROI

- 最小可行版：**不引入向量库**。以 SQLite FTS5（已有）+ 结构化过滤建"事实检索"：按本章出场人物 + 场景地点 + 伏笔状态，从圣经/台账/摘要里**只取相关的那些**，其余不进 prompt。
- 二期再上 embedding（本地 ONNX 或 API），做语义召回（Goink 路线）。
- 直接收益：草稿 prompt 从 31 块里真正"带进来"的降到 10 块以内；省下的注意力还给蓝图与戏剧任务；**治白水 + 治上下文膨胀 + 降成本，一箭三雕。**
- 前置：需要一次 A/B 评测（`evals` 底座现成）。

**② 场景级生成——章级单发改场景级串行** ⭐ 高 ROI

- `beats` 已经在蓝图层产出，把它从"提示文本"升级成"执行单元"：**每个节拍一次调用**，每次只带该场景需要的上下文。
- **场景级验收**：单场景生成后立刻用小模型判"这个场景有没有张力/有没有推进"，不合格当前场景重来，**而不是整章重来**（现在整章重写烧的是整章的草稿+定稿）。
- 直接收益：**"该精彩处放开、该压抑处压住"才真正落得下去**；顺带大幅降低回炉成本。
- 注意：这会增加调用次数（3 场景 ≈ +2 次创作调用），但能砍掉大部分整章回炉。

### 第二档 · 补关卡（1~2 周）

**③ 剧本 / 漫剧继承小说线的一致性能力**

- 把 `BibleService` 的**只读查询**开放给改编线：改编时对照"第 N 章时角色状态"，而不是只看一段正文。
- 给漫剧线补**格式门禁 + 版本快照**（剧本线今天刚补齐的，直接复用 `engines/script/common.py` 的实现）。
- 理由：你的路线是"小说→剧本→漫剧"，中间这环刚补上引擎，**下一环（漫剧）代码量最大却关卡最空**。

**④ 评测门槛进 CI（可行的那一半）**

- 把**确定性指标**在 mock LLM 下固定成 CI 门槛：AI 味指数、复读、篇幅比、blocker 生成逻辑、prompt 指纹变更检测。
- 补一次 **mutation test**：故意改坏一个 prompt，验证门槛确实报警——**这一步做完，门槛才算被验证过**。

### 第三档 · 还债与对外（穿插进行）

**⑤ 拆编排上帝函数**：把 `generate_chapter()` 的 `while True` 拆成命名的阶段列表（Planner→Composer→Writer→Auditor→Reviser 这样的显式结构）。**在加"场景级生成"之前拆，比之后拆便宜得多。**

**⑥ 双轨 schema 收敛**：`baseline_schema/` + `evals/fixtures.py` + 前端 `api.ts` 的字段清单，考虑从 models 单向生成，消灭"改一处要同步九处"。

**⑦ 文档一致性收尾**：把 `README_EN.md`、`docs/01-architecture.md`、`backend/README.md` 里残留的"可切 Postgres"改掉（主 README 已改）。

**⑧ 对外可信度材料**：用已有的免登录分享能力挂一本**真写出来的样例书** + 导出一份"本书健康报告"（AI 味曲线 / 一致性冲突曲线 / 每章成本）。这是我们唯一能正面回应 InkOS"33 维审计"的方式——**用事实，不用形容词**。
