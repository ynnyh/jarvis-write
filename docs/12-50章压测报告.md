### 关键发现:中转渠道 JSON 截断(隔离 0→9 的根因)

续跑 13 章里 **9 章被隔离**,全部是同一模式:**中转返回的 JSON 被拦腰截断**——
`Expecting ',' delimiter` 的报错位置恰好都落在返回内容的末尾,连
`{"issues": []`(16 字符,连收尾 `}` 都没有)也被截断,截断点从几十到五千多字符不等。
这不是 max_tokens 截断(截断点不固定),是**魔芋中转在响应体上丢尾巴**;官方 key 跑的
前 37 章(含大量同构 JSON 调用)零解析失败,对比鲜明。

**系统行为完全符合预期**:一致性检查/主审/契约提取拿到截断 JSON → 显式降级 →
该章 `quarantined` 待人工复核、跳过章后抽取/摘要防圣经污染。P0 修的降级链路
第一次在真实长跑里成规模触发,没有静默放行。同时:

1. 402 续跑链路端到端验证通过:恢复 13/13、JSON 原地更新(.bak 备份)、
   聚合重算,长程一致性(连贯性 8.17 vs 8.14)不受中断影响。
2. 续跑还顺手暴露并修掉一个真 bug(2b1734a):`resume` 子命令先导入 runner
   (连带建 engine)再设 `DATABASE_URL`,全新进程必连默认库;已改为先定位
   run 库再导入。
3. 正文质量本身没有掉:隔离 9 章是「校验没跑完」不是「写得差」——续跑章里
